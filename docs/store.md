# The sealed store

**The rule it follows**, as given (24 and 26 November 2026), quoted as it was written:

- 24 November: Sioul's own files go into a sealed store.
- "Obsidian notes vault is not supposed to be within Sioul encrypted store, it lives outside. Only client files are encrypted, but once decrypted, they stay .md and databases."
- ""seal everything" meant "every Sioul config file". It was explicitely stated that latters, papers and notes would stay out of it, hosted on the filesystem in clear for interoperability with the OS."
- "Placing notes, papers or letters folders inside Sioul folders could actually be a feature allowing implicit encryption at the sake of interoperability. It shouldn't be forbidden, but the GUI should make it clear that it's a tradeoff and explain what is gained, what is lost."
- And the ground of everything: "your admin stays usable without Sioul". Sioul has no private file format: what it keeps stays standard (`.md`, `.ics`, `.vcf`, Maildir, PDF, TOML, JSON), sealed on the disk and written out in clear by `sioul store export`.

So: every file Sioul keeps under its four folders (configuration, data, state, cache) is sealed on the device; the notes folder, the papers' and the letters' folders stay **outside, in clear**, unless the person places one of them inside Sioul's folders, after the window says what that gains and what it loses ([below](#your-folders-inside-sioul-s)).

Code: `crates/sioul-core/src/sealed/` (the door; `files.rs`, the door through paths every reader and writer uses; `moving.rs`, the move), `crates/sioul-sync/src/storekey.rs` (its key in the keyring, the window's start, the opener of every other program), `crates/sioul-cli/src/store.rs` (`sioul store`, `sioul settings`), `tools/check-store-door.py` (no file call around the door).

## What it guarantees, and what it does not

- **Sealed on the disk.** Each file is compressed and sealed (XChaCha20-Poly1305) under a key kept in the system's keyring. The names on the disk are opaque: a mailbox's folders, an account's name, a calendar's or a client's name, even whether a given file exists, say nothing there. Sizes and times still show.
- **Whole or not at all.** A write is made beside its place, flushed, renamed into place and its folder flushed, then one sealed line in its folder's journal makes the change: after a power cut, a reader finds the old content or the new, never half of one.
- **A failure is never an empty file.** A file that does not open is said damaged (`Error::Damaged`), never absent and never empty; a lock that cannot be taken is an error, never passed over. A reader that gets an error keeps what it has.
- **Earlier versions, to mend and to undo.** Every file that changes keeps its *n* earlier versions (2 until the person sets *n*): a damaged copy is mended from them, and any of them can be put back (`restore`), itself undone the same way. Whatever exists nowhere else (no server holds it, no other device has it yet) can be written twice at once (a twin), until its caller says it has travelled.
- **A wrong key is told at once**, from a value sealed in `store.toml`, before anything is read or written: never taken for damage.
- **What it does not do.** It does not hide anything from a program running as the person and reading the keyring (on Linux and Windows the keyring gives any program of the session what it holds, as for any application), nor from someone at an unlocked session. **Nothing here is a lock of Sioul's own**: the session's lock and the disk's encryption are the guards. It does not erase what a disk keeps of removed files (on flash, "removed" means unlinked); only the disk's own encryption covers that.

## Who reads what

| Who | What they read |
|---|---|
| A powered-off disk encrypted by the system (LUKS, FileVault, BitLocker; every Android) | nothing |
| A powered-off disk not encrypted | the blobs, their sizes and times; the keyring's file opens at the strength of the session's password, and with it everything Sioul keeps |
| Someone at the unlocked session, or a program running as the person | everything, as with any application that keeps a key in the keyring |
| A backup of the folders put back elsewhere | blobs, unreadable without the key |

## The door (`sioul_core::sealed`)

A file is named by a **logical path**: its first part one of the four folders (`config`, `data`, `state`, `cache`), the rest the layout of today (`config/config.toml`, `data/mail/<account>/<folder>/<unique>`). Any byte but a NUL, a slash or a backslash is allowed in a name, up to 255 bytes a part and 4 096 a path: the names on the disk are opaque, so no system's rule applies.

```rust
let store = Store::open(&Folders::of_profile(), &key, Options::for_profile("window"))?;
store.read(&path)?;                    // Ok(None): absent; Ok(Some(opened)); Err(Damaged | NotOpen | …)
store.write(&path, bytes, How::default())?;
store.update(&path, How::default(), &mut |old| Ok(Some(new_bytes(old))))?;   // read, change, write under the folder's lock
store.list(&folder)?;                  // one manifest read: names, sizes, generations, attributes
store.set_attrs(&message, &[("flags", Some("RS"))])?;                       // one journal line, the blob untouched
store.append_line(&log, line)?;        // a file that only grows, sealed line by line
store.versions(&path)?; store.restore(&path, generation)?; store.purge(&path)?;
```

The contract other changes code against, with every call and error: the module's own documentation (`cargo doc -p sioul-core`), its tests (`sealed/tests.rs`), and the errors: `Absent` (never written, or removed), `Damaged` (named, and no copy opens), `NotOpen` (no store in this process yet: its key is not had), `WrongKey`, `Changed` (written meanwhile: read again), `Locked`, `NoRoom` (the old content intact), `Synced` (the store refuses a folder a sync app carries), `Refused`.

## Paths: how every reader and writer reaches it (`sealed::files`)

Sioul's code reads and writes files by their paths, through `sioul_core::sealed::files` (each crate names it `crate::files`): the standard library's calls with the same shape (`read`, `read_to_string`, `write`, `rename`, `copy`, `remove_file`, `create_dir_all`, `read_dir`, `metadata`, `exists`, `File`, `OpenOptions`, `DirBuilder`), and `Probe` (`present`, `present_file`, `present_dir`) for what `Path::exists`, `is_file` and `is_dir` would answer of the system's files alone. `std::fs` is used nowhere else but in the door itself and in `filelock.rs` (which keeps the system's mechanics for a file of the system: written beside and renamed, overwritten before it goes, read through its descriptor, and takes the door's way at each entry for a sealed file).

- **A path under one of the profile's four folders** is a file of the profile's store, under its logical path (`<config>/config.toml` is `config/config.toml`, `<data>/mail/<account>/INBOX/cur/<name>` keeps its name): the layout of today, so that the export is that layout in clear. **Any other path** (the notes folder, papers and letters outside, a file the person picks, the sharing folder, a temporary folder) is the system's file, as before.
- **What stays in clear inside Sioul's folders, by rule** (`files::stays_plain`): the store's own files (`sealed/`, `store.toml`); lock, process and socket files (`*.lock`, `*.pid`, `*.sock`: empty, or a number; a sealed file's lock at an opaque place, below); and what another program reads or writes by its path: the sounds Qt plays (`cache/sounds`) and the voice messages of calls (`cache/calls`), icons and pictures Qt shows (`cache/favicons`, `cache/photos`), a text's media while shown (`cache/texts`), copies of attachments opened in another application (`cache/attachments`, `cache/texts-attached`), a voice memo while Qt records it, before it is sealed into the notes (`data/memos-recording`, outside the cache, which is emptied), files a site downloads, which Chromium writes (`cache/downloads`), files chosen in a dialog while they are copied (`cache/chosen`), the pages Poppler and Tesseract read a scan from (`cache/ocr`), Qt's own caches (`cache/qmlcache`, `cache/qtpipelinecache*`), the spam filter's and the topics' training input, which fastText reads by its path (`cache/spam`), a spam job's error output, which its own process writes (`state/spam/jobs/*.log`), the virus scanner's database (`data/clamav`) and Chromium's profile where a system puts it inside the data folder (`data/QtWebEngine`), and the plain copy the move holds aside for a moment while it checks it (`<folder>/sealed-moving/`). A copy in clear of a sealed paper, letter or note opened in another program goes to the session's runtime folder (`$XDG_RUNTIME_DIR/sioul-opened-<profile>/`, in memory, gone at the session's end; without one, `cache/attachments/opened/`), emptied at each start. The other caches above are Sioul's, made again, and the disk's encryption covers them.
- **Which store**: those mounted in the process (`files::mount`, a guard: the window's, a test's), else the profile's own once `store.toml` exists, opened at the first call that needs it by the opener the program set as it started (`files::set_opener`; `storekey::open_on_demand` reads the key from the keyring without ever asking it to open). **While it cannot be opened** (the keyring locked) every call under the profile's folders fails, `NotOpen`: a program never reads or writes a plain file beside a sealed profile.
- **A write to the system's file under the profile's folders** (before the profile is sealed, or a file the move has not taken yet) holds the profile's lock shared (`plain_write`, and `files::while_plain` for `filelock`'s own writes), so that the move never runs under a writer; under the lock the path is routed again, and a file the move took meanwhile is written through the store (`Rerouted`), never in clear where the move just removed it. A read that finds a plain file gone that the store now holds is routed again too: a file being moved never reads as gone.
- **Folders inside the store are implicit**: one exists while a file lives below it, or since this process made it (`create_dir_all`), until it is removed; the store keeps no empty folder. `read_dir` gives a folder's files from its list, the folders below it, and what stays in clear there by name.
- **A file held open** (`File`) is read whole when it is opened and held in memory; one opened to write is sealed at `flush`, `sync_all`, `sync_data` and when it is let go. Appending rewrites the file whole: fine for Sioul's logs, which are small; one that grows large is a file that only grows (`append_line`) to move to later.
- **Earlier versions**: a cache's files and a mail message (`data/mail/…`) are written `unversioned` (made again, or kept by their server); everything else keeps its *n* earlier versions.
- **Locks of a sealed file** (`filelock::with_lock`) are under its store's `sealed/.locks/`, their names opaque (`files::lock_place`): a lock beside the file would name it in clear.

- **What the disk holds.** A link, and whatever lies behind one, stays the system's, read and written as before: a configuration linked from a dotfiles folder, a calendar folder on another disk. So does a plain file in a folder the move has not taken yet, and one the move could not take (noted as left) or put back after a write reached it while it was moved: a path that exists is never read as gone (a calendar sync would take a file it does not find for one deleted here). **In a folder moved before, a plain file is not the profile's**: written there since by a process that does not know the store (an older Sioul still running, an agents' server started before the update, another program, a backup put back by hand), it is never read as current; reads and writes of its path go to the store, and the next start sets it aside (below). A folder alone is the store's.
- **Lock files never name what they lock.** A `*.lock` whose file is sealed (`filelock`'s `.<name>.lock` beside it, an account's `state/dav/<id>.lock`, any lock named after a folder or an account) lives at an opaque place under its store's `sealed/.locks/` (`files::lock_target`), whatever path the code gives; the empty lock files of the layout before are taken away by the move once nobody holds them. Only the profile's own (`.profile.lock`, `.store-create.lock`) and those beside what stays in clear keep their names.
- **Held files keep the system's meaning**: an append adds to the file as it is now, under its folder's lock (no other writer's line lost); `create_new` claims the file at once; `lock` and `try_lock` lock the file's opaque lock; a small write seals at once and returns its error. Each later seal of the same handle replaces the content it sealed first without making an earlier version of it (`Store::amend`), under a generation of its own, the replaced blob going once the new line is written: a power cut at any step leaves the old content or the new, whole.
- **Room**: earlier versions go first when the disk is short; a current write is refused only by a disk really full, the old content intact.
- **Sioul's own lists still in the notes folder** (a device that has not moved them to `data/records/`) stay in clear there, as the notes do, until they move; the card "What Sioul keeps here" says so.

## Your folders inside Sioul's {#your-folders-inside-sioul-s}

The notes folder, the papers' and the letters' folders, and where scans arrive, are the person's, outside Sioul's folders by default, in clear, for Obsidian, Nextcloud Notes, the file manager and the system's search and previews. **Placing one inside Sioul's folders is allowed**, as a trade the person makes: where such a folder is chosen (a folder's row in Settings, the papers' and letters' folders in the window of the move of the lists), one paragraph says it (`folder_sealed`, words `storage-sealed-tradeoff`): what is gained (the folder is sealed on the disk, unreadable without the session on a lost or stolen device, carried sealed) and what is lost (Obsidian, Nextcloud Notes, the file manager, the system's search and previews no longer read it; getting the files out takes Sioul or `sioul store export`).

Placed there, a paper, a letter or a note's file opens in another program through a copy in clear (in the session's memory-backed runtime folder where there is one, emptied at each start), and a voice memo is recorded in clear beside (`data/memos-recording/`), then sealed into its place when it ends, or at the next start when Sioul stopped meanwhile. Placed there, the folder's files are sealed by the same routing as everything else: the notes', papers' and letters' readers and writers need nothing of their own, they already go through `files`. **The move never seals such a folder where it finds it**: one that lies inside Sioul's folders when they are first sealed (placed there before this version) is kept in clear there (`Store::keep_in_clear`, a list sealed in the store; `files::would_seal` then says no paragraph for it), until the person chooses otherwise where the folder is set, with the paragraph above; one placed there later, knowing the trade, is sealed, and plain files found in it at a start are sealed in place. Where these folders are is read from the configuration by the process that moves (the screen before the window is one of its own), as the configuration is on the disk then; a configuration that does not read stops the move rather than seal a folder where it lies.

## The move {#the-move}

At the window's start, before any other file is read (`storekey::begin`, then the screen before the window, below): the profile's store is opened (the keyring may ask to be opened; the screen waits for it, and the window never starts on an empty profile beside the store); or, when the profile has none, it is made (its key kept in the keyring first; with no keyring to keep it in, the profile stays in clear this time and the next start tries again) and **every plain file is moved in** (`Store::move_plain_files_beside`): under the profile's lock held exclusive (every other writer of Sioul waits), one folder of the four after the other. Each file is read and sealed (streamed past 32 MB) while it stays where it is, so that a reader goes on reading it; then it is renamed aside (`<folder>/sealed-moving/<its path>`), found unchanged (its number, size and time) and the same as its sealed copy, and only then removed. Sioul's own writers wait meanwhile (the profile's lock). Another program's write that reached the file before it was found unchanged puts it back where it was (what it held then sealed as the file's newest version), to be taken at the next start; one made by its path once it was renamed aside makes a new file there, read as the profile's and taken at the next start. Only a write through a descriptor that program opened before the rename and that lands in the instant between the check and the removal is not seen. Folders left empty go. A move stopped half way goes on at the next start, the plain files being the truth until they are gone, and the same content is never sealed twice; a copy a cut left aside is found first: one a version of its file holds goes, one never sealed goes back to its place, any other is sealed apart under `data/set-aside/<day>/` and said once (`store-set-aside`). Each folder done is marked moved for good in the store.

**A file the move cannot take** (unreadable, a name the store cannot hold, the disk full, a file written to while it was moved) stays where it is, in clear, read as before: said once by the window (`store-left-plain`), noted in the store (`left`, with its size, time and number), tried again at the next start away from the window (`Store::retry_left`), and never counted again for the screen before the window until it changes. The window always opens.

**A plain file found later in a folder already moved is set aside**, never sealed over the current file: written by an older Sioul still running, an agents' server of the version before, another program, or a backup put back by hand, it was never read as current meanwhile (above), so nothing this version wrote is rolled back, and nothing an old process wrote becomes the truth without the person's word. It is sealed under `data/set-aside/<day>/<its path>`, and the window says once how many and where (`store-set-aside`); `sioul store bring-in data/set-aside/<day>/<its path>` takes one in on purpose, what it replaces kept as an earlier version. Two kinds stay the profile's and are sealed in place: a file the move noted as left, tried again; and a new file in a folder of the person's placed inside Sioul's knowingly (one whose path the store does not hold yet; one that would replace a sealed file is set aside like the others).

Only the window moves; the command line, the watcher and the agents' server open a sealed profile at their first file call, and work in clear on a profile not sealed yet.

**On Android the store is not turned on yet**: Java reads several of Sioul's files there by their paths (the doses' alarms, the home card, texts sent), so the phone's files stay as they are until those readers go through the door (`store-android`). The sharing between a phone and a computer is unchanged (below).

## At start: the screen before the window {#at-start}

The window's start opens what Sioul keeps before any other file is read (`storekey::begin`, quick: it never waits). When the keyring gives the key at once and nothing is left to move, the window opens as before. Otherwise a screen comes first (`sioul-app/src/storegate.rs`, `StoreGateWindow.qml`), and the window opens only once the store is open:

- **The keyring not open yet**: "Sioul waits for your keyring to open." The keyring is asked once (it may ask for the session's password), then looked at again each second, quietly; Sioul goes on by itself. **Use a way back…** shows the ways back meanwhile.
- **The keyring holds no key for it any more**: said, and the ways back shown at once: the passphrase (with the day it was kept, and whether it was the sharing's then), the recovery code, the security key with its PIN. A key a way back gives is kept in the keyring again when the keyring takes it, so that the next start needs nothing; when it does not (locked for good, no keyring at all, an item refused), Sioul opens all the same. Without any way back: **Start again from your servers and your other devices**, offered only here (never while the keyring is merely locked, and asked again of the keyring when pressed), and only once a second step said what it sets aside and the person confirmed. A new key is kept in the keyring and read back first, so that nothing is set aside when the keyring cannot keep one; then what is sealed is set aside whole (`sealed-unopened-<when>` beside each `sealed/` folder, `store.toml` with it: never removed) and a new store is made. `sioul store reopen` lists what was set aside and its ways back, and `sioul store reopen <when>` opens it again with one of them (its passphrase, `--code`, `--card`), putting it back as what Sioul keeps here (the store made meanwhile set aside in its turn, never removed; Sioul's window closed meanwhile); from there `sioul store export` writes it out. Mail, agendas and contacts come back from their servers, and what the sharing carries from the other devices once this one joins it again with its passphrase.
- **Plain files to move** (the first sealing, a move stopped half way, files written in clear since): the move's progress, file by file; stopped, it goes on at the next start where it stopped. At the first sealing, the ways back are then offered once (below), and the window opens on **Open Sioul**, whatever stays in clear (said once in the window).

The screen is a process of its own (`sioul-app --store-gate`), which the window starts and waits for. At its end it hands the window the key the store opened with and what is said once, on a pipe of the window's own whose end the screen gets as its descriptor 3 (`SIOUL_GATE_HAND_OVER`; taken only when it is one end of a pipe, then kept closed to any program the screen starts): never its standard output, so that a terminal or a log never shows the key, and nothing of it touches the disk. The window opens the store with that key, whatever the keyring does. The screen run by hand, or on a system without such a pipe (Windows, macOS), hands nothing, and the window asks the keyring itself. The window listens for later starts of Sioul before it opens anything (`outside::listen`): a start made while the screen shows (the icon clicked again, a mail link, a calendar file) hands over to it, what it handed waiting in memory until the store is open; never a second screen, a second store made, or a second window.

## Ways back {#ways-back}

The root key lives in the keyring alone until the person keeps a way back. Each way is an option the person chooses (the rule of 24 November: no lock beyond the system's, each protection explained), offered once at the first sealing and always on the card "What Sioul keeps here" (Settings ▸ Your folder and sharing), with what it protects against; none is made without being asked. Each is the root key sealed under another secret, kept in clear in `store.toml` (both copies, `[[ways]]`: an older Sioul passes over them), and each is checked against the store before it is kept and when it is used (`sealed::key_opens`):

| Way | Sealed how | Protects against | Cannot |
|---|---|---|---|
| A passphrase (the sharing's, if the person likes; 12 characters at least) | Argon2id (64 MiB, 3 passes) as the sharing's, then XChaCha20-Poly1305, bound to the way and the store's id | a keyring lost or reset | a passphrase forgotten; whoever knows it and holds the disk opens the store |
| A recovery code: 32 random bytes shown once as 13 groups of four (Crockford's base32: no I, L, O, U; typed back in any case, with spaces or dashes) | HKDF-SHA-256 of the code (256 bits: no stretching), then XChaCha20-Poly1305 | a keyring lost | a code lost; a new code replaces the one before |
| The person's security key (each one Sioul knows that decrypts) | an OpenPGP message to the card's encryption key (no PIN to seal); beside it only what finds the card and opens the message: the card's serial, the fingerprints of its certificate and of its encryption key, and the certificate stripped of its names and addresses | a keyring lost, while the card and its PIN remain | a card lost, reset, or given a new encryption key (its way is then said stale on the card, to keep again) |

A passphrase way stays the passphrase it was kept with: changing the sharing's passphrase later does not change it, and the screen says the day it was kept. The cost Argon2id is asked is read from `store.toml`, never more than Sioul writes there (64 MiB, 3 passes): a damaged or forged file never makes a try take gigabytes or minutes.

**With no way back kept**, the card says plainly what a lost keyring entry would cost: what only this device holds; mail, agendas and contacts come back from their servers, and, when the device shares, what the sharing carries from the other devices.

Not built: the root key sealed into the sharing folder itself (the design's first way back), a way back on a phone (the store is not turned on there), a passphrase asked at each start on a system with no keyring (`wrapped`: the command line's way only).

## Devices of other versions

- **Through the sharing**: nothing changes. The sharing folder lies outside Sioul's folders and keeps its own format (sealed records, `docs/database.md`); a device on an older version and one whose files are sealed read and write it alike, each writing what it receives into its own files, sealed or not.
- **On the same device**: an older Sioul started on a sealed profile finds no configuration and starts as a new, empty profile; what it writes is never read by this version and is set aside at its next start (above). The watcher and the agents' server follow their program's file and run the new one within seconds of an install (`mcp/follow.rs`, `remind.rs`), so on Linux only those seconds, a long call, a training started by the old window, and other programs remain. A device whose files were sealed must not run an older Sioul; `sioul store unseal --to DIR` writes the whole profile in clear in its old layout, for that.

## The export {#the-export}

`sioul store export --to DIR` writes every file Sioul keeps in clear under `DIR`, at its logical path, so in the layout Sioul has always used: `config/config.toml`, `data/mail/<account>/<folder>/cur/…` (Maildir), `data/calendars/…/*.ics` and `data/contacts/…/*.vcf` (vdir, which khal, khard and vdirsyncer read), `data/records/*.toml`, `state/…`. A file that only grows is written as its lines. Health and the person's own keys go too (it is their copy); a client's file only with `--clients`. A file that does not open is said and skipped (`sioul store check` names it). `DIR` must be empty and outside Sioul's folders.

## Locks

The door takes its own: each logical folder's lock (exclusive for a change, shared for a read), and the profile's lock (`<config>/.profile.lock`), shared around every change, which the move and `check --repair` take exclusive so that nothing writes meanwhile. A writer of a plain file under the profile's folders takes the same profile lock (`ProfileLock::shared`) before it writes, and asks its route again under it. Inside an `update`'s change, the store refuses its own folder rather than write under itself.

## The format

- **A blob**: a clear header (`sioul-sealed`, the format, its role, its copy, its piece size, its generation), then pieces of 64 KiB, each sealed with XChaCha20-Poly1305 under a random 192-bit nonce and bound to the clear header, the blob's own name, the piece's index and whether it is the last, as the sharing binds its pieces (`sioul-sync/src/blobs.rs`). Piece 0 holds the logical path, when and by whom it was written and whether the content is compressed, padded to 512 bytes so that its length says nothing of the path's; the pieces after it the content, compressed (gzip, its fastest level) unless its writer said not (`How::uncompressed`, for what an outsider can drive the size of); the last one its size. A blob copied under another name, or an older generation put in a newer one's place, does not open there; a copy is read only when its sealed bytes are the ones its record names. A format this Sioul does not know is damage, never "a newer Sioul": the store's own format is said by `store.toml`, not by a byte a flipped bit can change; an error of the disk stays one, and the next copy is tried.
- **Names**: base32 (lower case: one name on systems that ignore case) of HMAC-SHA-256 under the naming key, of the role, the path, the generation and the copy; stored as `<folder>/sealed/ab/<the rest>`.
- **Manifests**: one per logical folder (each file's generation, sizes, the hash of its sealed bytes and of its twin's, its versions, its attributes; the highest generation the folder ever gave, so that a generation never comes back and an old blob of a path removed, purged or renamed never opens as a new file there), written twice, and a journal of sealed lines bound to the folder and the manifest's generation, folded into a new manifest past 512 lines or 256 KiB. A root manifest per folder of the four lists its logical folders. Lost or damaged, a manifest is **made again from the blobs** (each opens by its own name and gives its path), what its other copy and its journal still say laid over them; a file its list named and no blob holds stays named, damaged. Attributes (mail's flags) live only there: lost with every copy of the list, they come back from the mail's server.
- **Files that only grow** (logs): each line sealed alone, its number in clear and bound to it and to the file's own name; a line that does not open is that line lost, whatever it did to the line ends; a head that does not open stops nothing; the record keeps the count, so that a cut at a line's end is seen. What exists nowhere else has every line in two copies (`How::only_here`).
- **Formats and their versions.** `store.toml` says the store's format (1); a newer one is refused whole ("this store was made by a newer Sioul"), never read in part. A blob's and a line's own format byte is damage when unknown, never "newer". A manifest's records carry the fields they do not know through a fold (`Rec::rest`, `Ver::rest`): a later Sioul may add a field to a record without changing the format, and this one keeps it; a change of meaning changes `store.toml`'s format. The move's progress is the store's own record (`moved`), never going back; the files it left in clear are another (`left`: each one's size, time, number and its number's change time, then its logical path, a line each), kept only while there are some.
- **`store.toml`**, in clear on purpose: the format, the store's id (what its key is kept under), the check value; on a system without a keyring, the key wrapped under a passphrase. Kept twice (beside the configuration and in the data folder's `sealed/`), both tried, written last when a store is made; a store is never made over sealed files whose `store.toml` is gone.
- **Keys**: one root key per store, 256 random bits, kept as "Sioul store <id>" in the keyring (the Secret Service, the Credential Manager, the Keychain, Android's KeyStore). From it, HKDF-SHA-256 (salt: the store's id) makes the sealing key, the naming key, the lines' key and the check key; the root key seals nothing itself.

## Earlier versions and their collection

*n* is one value for every file, kept in the store itself so that every process has the same (`Store::set_versions`; 2 until set). A write makes the replaced content an earlier version where it lies, and takes out the one beyond *n*; a removal keeps the removed content as an earlier version (so it can be put back), unless *n* is 0 or the file is one that never changes and has a source (`How::unversioned`: a message), whose removal is final. The collection (`Store::collect`, run when idle, under the profile's lock held exclusive) follows the sharing's earlier versions (`history.rs`): by count, then by size past a GB (or a twentieth of the disk if less) in each of the four folders, the oldest first. When the disk is short (less than a quarter of a GB, or a hundredth of the disk, would be left), earlier versions go before a write is refused; never a twin, never a file's last good copy. It finds folders from their lists and from the blobs, takes a blob newer than its list as its file's content (a backup put back, an interrupted write), and removes only blobs that open with this store's key and that no list names. A purge takes out every blob of the file (every generation its folder gave, both copies, the copies set aside) first, then its record, and writes its folder's list again at once so that no list names it; `purge_under` does so for everything under a folder (a client's file erased).

## The check

`sioul store check` opens every piece of every file, twin and earlier version, and says by folder how many files are whole, how many good copies each has, what is lost here; `--repair` sets damaged copies aside (`sealed/.aside/`, removed after 30 days), makes a damaged current copy again from its twin or puts its newest good version back, takes a blob newer than its list as the file's content (an interrupted write, or a list put back older), and takes out blobs no list names.

## What each system does

- **Linux, Android, the BSDs, macOS**: a folder is flushed by `fsync` on it, so that a rename survives a power cut; folders 0700, files 0600.
- **Windows**: a folder cannot be flushed (NTFS journals its names itself); a rename over a file that an indexer or an antivirus holds a moment is tried again for a tenth of a second.
- **Android**: the app's private folders. Java's own files (its preferences, the wake-up list read before the first unlock) are not reached by the door; a later change seals what Java reads with a KeyStore key.
- **A folder a sync app carries** is refused (`Error::Synced`): recognised by Nextcloud's, Syncthing's and Dropbox's lists, the usual names in the home folder, and a sync app's own mark in the folder or above it.

## Starting, waiting, and tests

The key comes before the configuration. `storekey::root_key` reads it without ever asking the keyring to unlock: a keyring there and not open yet is `Locked` (wait for it), no keyring service at all is `NoService` (a passphrase stands in, Argon2id as the sharing's), no key for this store is `Missing` (a way back is needed). `storekey::wait_for_root_key` waits for the keyring and never prompts, for the watcher started at login, which systemd gives up on after five failed starts.

Tests and the demo never reach a keyring: the core's tests use `RootKey::test()`, another crate's tests turn on the `test-store-key` feature and set `SIOUL_TEST_STORE_KEY`. That feature is never in Sioul's builds; it leaves the mark `SIOUL_TEST_STORE_KEY` in a binary, which `tools/check-test-marks.sh` refuses in anything about to ship (the packages' workflows, the Flatpak, `install.sh` and `final-pass.sh` run it).

## Words

"Store" is the developers' word, and the command's (`sioul store`). What people read never names it: the window and the guide say "what Sioul keeps on this device" (« ce que Sioul garde sur cet appareil ») and that it is sealed (« scellé »); the card in Accounts is "What Sioul keeps here" (« Ce que Sioul garde ici »). In French, never « magasin » nor « coffre » (the password manager's vault). Earlier versions are "earlier versions", « versions précédentes ».

## Commands

```
sioul store ls [PATH]                   a folder's files: sizes, generations, copies
sioul store cat PATH                    a configuration file unsealed to the standard output
sioul store put PATH < FILE             a configuration file sealed from the standard input
sioul store edit PATH                   in $EDITOR, through the memory-backed folder (Linux)
sioul store versions PATH               a file's earlier versions
sioul store restore PATH --version N    one put back (undone the same way)
sioul store check [--repair]            the check
sioul store export --to DIR [--clients] every file in clear, each in its standard format
sioul store unseal --to DIR             the store's files in today's plain layout, for an older Sioul
sioul store reopen [WHEN] [--code|--card]  what "Start again" set aside: listed, or opened again with a way back and put back
sioul store bring-in PATH [--any]       a file set aside at a start taken in on purpose, what it replaces kept
sioul settings get KEY | set KEY VALUE  one setting, as the window changes it, in the configuration where it lives now
```

`cat`, `put` and `edit` reach the configuration (`config/`) by default; any other file only with `--any`, and a client's file only with `--clients`; `ls`, `check` and `unseal` neither name nor write out a client's file without `--clients`, nor health or the person's own keys without `--any`. `put` and `edit` refuse a file that does not read as its kind (TOML, JSON) and a file changed meanwhile; each write keeps the replaced version; `cat` says when what it prints is an earlier version; `edit` keeps the edited copy when the write is refused. `sioul settings set` takes its value in JSON and goes through `settings::change`, as the window; the settings the window handles itself (a key, a folder moved) are refused, and a change after which the configuration no longer reads is undone.

## Bench

`cargo test --release -p sioul-core --lib sealed::bench -- --ignored --nocapture` seals a made-up profile of 6 000 files and 600 MB (one folder of 3 700 messages) and measures sealing and opening, listing that folder, one flag changed, a write with *n* = 2 and the check's full pass. The figures of the first run are in the change's notes; nothing is promised to the person before a bench on the phone too.
