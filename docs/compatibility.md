# Compatibility: what Sioul needs from servers and programs

What Sioul relies on in each protocol, what a server or another program must do for each feature, and how far each was tried. Read from the code at 098a9d5 (6 October 2026), for developers and server admins. The same for people using Sioul, in plain words: the guide's [Works with](https://sioul.aurelienpierre.com/guide/compatibility.html).

Each line says how sure it is:
- **Tested**: run against the server, program or device named; where that is recorded is in the last section.
- **Expected**: built to the standard named, not run against that one.
- **Limit**: what breaks or degrades, and why.
- **Not supported**: not built.

## Mail: IMAP
Code: `crates/sioul-sync/src/imap.rs` (the session), `fetch.rs` (fetching, IDLE), `mailbox.rs` (folders, what you do to messages).

| What | Standard | Used for | Without it |
|---|---|---|---|
| IMAP | RFC 9051 (IMAP4rev2), RFC 3501 (IMAP4rev1) | everything below | — |
| TLS from the first byte (993), or STARTTLS (143) | RFC 8314; RFC 9051 §6.2.1 | every connection; certificates checked against the system's store (rustls, Mozilla's list when the system has none) | no plain connection: refused. A certificate the system does not trust (Proton Mail Bridge's own, a self-signed one) is refused too |
| LOGIN, with the password | RFC 9051 §6.2.3 | signing in | AUTHENTICATE XOAUTH2 for Google accounts signed in with Google (a key of the person's own: [google.md](google.md), "Mail"), and for Microsoft's mail, which takes no password (Outlook.com, Hotmail, Live and MSN since 16 September 2024; Microsoft 365, no Basic authentication for IMAP in Exchange Online): signed in on Microsoft's page ([microsoft.md](microsoft.md)), **expected**, tried against stand-ins of Exchange only. OAUTHBEARER (RFC 7628) is not used |
| EXAMINE; UID FETCH with BODY.PEEK[] | RFC 9051 §6.3.3, §6.4.5 | fetching without setting any flag | — |
| UID SEARCH (SINCE, UID n:*); UIDVALIDITY, UIDNEXT | RFC 9051 | what is new, by UID; a new UIDVALIDITY fetches the folder again | without UIDNEXT, a folder empty in the first window is searched again by date |
| RFC822.SIZE | RFC 9051 | older mail sized before it is fetched, against the disk's reserve ([client.md](client.md), rule 7) | — |
| IDLE | RFC 2177 | the inbox kept open, renewed every five minutes: a code within seconds | the inbox is looked at every two minutes (`POLL`) |
| MOVE | RFC 6851 | archive, trash, junk, move | UID COPY, then `\Deleted` and UID EXPUNGE |
| UIDPLUS (UID EXPUNGE) | RFC 4315 | removing only the message moved or deleted | without MOVE and UIDPLUS, the copy is made and the original stays marked `\Deleted`: a plain EXPUNGE could remove what another client marked. Most clients hide it |
| SPECIAL-USE | RFC 6154 | Sent, Drafts, Junk, Trash, Archive, All | folders found by name (`folders::preferred`); a Trash, Junk, Archive or Sent missing is created, under `INBOX.` where the server keeps its folders there |
| `\Flagged` and `\Important` views | RFC 6154, RFC 8457 | left out (Gmail's Starred and Important); Gmail's All Mail is the archive when no folder says `\Archive` | — |
| Keywords `$Junk`, `$NotJunk` | IANA's IMAP keywords (RFC 5788) | told to the server's spam filter on Junk, Not junk and Not spam; kept at each sync in the file name (Dovecot's letters), for the Porch and the spam filter | a server that refuses keywords still gets the move; "Not spam" is then kept in this device's label log only |
| CONDSTORE: SELECT (CONDSTORE), FETCH MODSEQ, UID STORE (UNCHANGEDSINCE) | RFC 7162 §3.1 | the inbox's filters only: their claim on a message, the keyword `$SioulFiltered`, is set (and a mark another device left is taken off) only if nothing changed the message since its flags were read, so that of two devices fetching it in the same instant, one acts ([client.md](client.md), "Filters"; `crates/sioul-sync/src/filters.rs`). **Expected**: this path has not been run against a server known to offer CONDSTORE | the flags are read, then the mark set: two devices would have to read within the same round trip. A server that keeps no keywords of its own (no `\*` in PERMANENTFLAGS: Exchange, Outlook.com) cannot carry the mark at all: each device acts on what it fetched |
| CREATE, DELETE, STATUS (MESSAGES) | RFC 9051 | "New folder…"; deleting a folder only when it is empty and has no purpose | — |
| APPEND | RFC 9051 | the copy in Sent (`\Seen`); a message moved to another account, with its `\Seen`, `\Flagged` and `\Answered` | at Gmail (`imap.gmail.com`) and Microsoft (`outlook.office365.com`) no copy: they file their own |
| Modified UTF-7 folder names | RFC 3501 §5.1.3 | names typed with accents | — |

Microsoft's rule for Outlook.com, "Basic Authentication no longer available to access any Outlook account" from 16 September 2024: [Modern Authentication Methods now needed to continue syncing Outlook Email in non-Microsoft email apps](https://support.microsoft.com/en-us/support/known-issues/modern-authentication-methods-now-needed-to-continue-syncing-outlook-email-in-non-microsoft-email-ap).

**Not used**: CONDSTORE and QRESYNC (RFC 7162) for keeping folders in step: flags and deletions made elsewhere are found by asking the FLAGS of every message kept here, at each full round (`mailbox::reconcile`), which is slower on big folders; asking only what changed is planned ([porch.md](porch.md), "Next"). CONDSTORE serves only the filters' claim, above. METADATA (RFC 5464), considered for the Porch's marks ([database.md](database.md), "Not built"). JMAP (RFC 8620, RFC 8621): an account kind in the configuration (`AccountKind::Jmap`), no client. POP3, Exchange (EWS, ActiveSync): none.

**What another client on the same mailbox sees** (Thunderbird, a phone's mail app, the webmail):
- Fetching sets no flag. Opening a message in the window sets `\Seen`, as any client does; read, unread and flag are `UID STORE` with `.SILENT`.
- Archive, delete, junk and move reach the server ten seconds after the act (the "Undo" window), as moves.
- Replying sets no `\Answered`, forwarding no `$Forwarded`: nothing stores them.
- Drafts stay on the device; the server's Drafts folder is fetched like any folder, never written ([database.md](database.md), "Not built").
- What Sioul alone knows (the Porch's lanes, senders' lists, links) stays on the device and travels by the sharing log, never in IMAP.

## Mail: SMTP
Code: `crates/sioul-sync/src/send.rs`, on `mail-send` 0.6.
- **Submission** (RFC 6409) on 465 with TLS from the first byte (RFC 8314), or on 587 with STARTTLS (RFC 3207). A server that offers no STARTTLS on 587 is refused; there is no plain option.
- **AUTH** (RFC 4954) with the password: PLAIN (RFC 4616), LOGIN, CRAM-MD5 (RFC 2195) or DIGEST-MD5, as the server offers them. For accounts signed in with Google or Microsoft, `AUTH XOAUTH2` with an access token, written by hand (`sasl.rs`); no OAUTHBEARER. Microsoft's two sending servers are on 587 only, with STARTTLS.
- **EHLO** with the address literal `[127.0.0.1]` (RFC 5321 §4.1.4), not the computer's name, which providers copy into the `Received` header everyone reads.
- **The message**: MIME, `multipart/alternative` (the Markdown as text, and HTML); `In-Reply-To` and `References` (RFC 5322 §3.6.4); PGP/MIME when signed or encrypted (below); an `Autocrypt` header when you have a key.
- **The copy in Sent**: IMAP APPEND, read, except at Gmail and Microsoft, which file their own. A copy that could not be filed is said; the message is not sent again.

## Finding servers
- **Mail** (`discover.rs`): Thunderbird's autoconfiguration format, HTTPS only: `https://autoconfig.<domain>/mail/config-v1.1.xml`, then `https://<domain>/.well-known/autoconfig/mail/config-v1.1.xml`, then Mozilla's ISPDB (`autoconfig.thunderbird.net`, told the domain only), then a guess (`imap.<domain>`, `mail.<domain>`, port 993), said as a guess. **Not used**: SRV records (RFC 6186), which [architecture.md](architecture.md) names; Microsoft's Autodiscover.
- **Calendars and contacts** (`dav.rs`, `candidates`): the address given; RFC 6764's `/.well-known/caldav` and `/.well-known/carddav` on the domain and on `caldav.` and `carddav.` hosts; the known places of murena.io and e.email, fastmail.com, icloud.com and me.com, posteo.de, mailbox.org; port 2080 of the mail server (cPanel hosts). No SRV or TXT lookups. Redirections are followed by hand, five at most, within the same domain (`sites::domain_of`), Google's excepted: each request carries the password.
- **What a server offers** (`scout.rs`): a Nextcloud's `status.php` (product, version) without a password; its OCS capabilities with the calendars' password, to name its apps (calendars and contacts are taken; Files, Notes, Talk, Deck, Mail, Bookmarks, Tables, Forms and Photos are said "not yet").

## Calendars and contacts: CalDAV and CardDAV
Code: `crates/sioul-sync/src/dav.rs`, a small client on `ureq` and `roxmltree`; the files on disk in `crates/sioul-core/src/vdir.rs`.

| Request or property | Standard | Needed for | Without it |
|---|---|---|---|
| HTTPS, Basic authentication | RFC 9110, RFC 7617 | every request | plain HTTP refused (test builds aside). **Not supported**: Digest (RFC 7616), Negotiate, client certificates. Baïkal's default is Digest: set its "WebDAV authentication type" to Basic |
| A bearer token | RFC 6750 | Google only | — |
| `current-user-principal` | RFC 5397 | finding the account | the address asked is taken as the principal |
| `calendar-home-set`, `addressbook-home-set` | RFC 4791 §6.2.1, RFC 6352 §7.1.1 | finding the collections | not found: the server's address must be given |
| PROPFIND Depth 1: `resourcetype`, `displayname`, `getetag` | RFC 4918 | listing collections and items | — |
| `current-user-privilege-set` | RFC 3744 §5.4 | collections that can only be read (none of `write`, `write-content`, `all`, `bind`) | taken as writable |
| `supported-calendar-component-set` | RFC 4791 §5.2.3 | which calendars hold tasks (VTODO) | a calendar that says nothing is offered for events and tasks |
| `schedule-calendar-transp` | RFC 6638 §9.1 | a calendar that takes none of your time as a whole (`transparent`): its events hold no time and make no conflict ([client.md](client.md#conflicts)) | opaque, as the RFC has it |
| `calendar-color` | Apple's namespace, `http://apple.com/ns/ical/` | a calendar's colour | none |
| `getctag` | CalendarServer's namespace | a collection unchanged since the last round is not compared | its items' tags are compared each round |
| REPORT `sync-collection`, `sync-token` | RFC 6578 | only what changed | every item's `getetag` (PROPFIND Depth 1), compared with what is known: slower |
| REPORT `calendar-multiget`, `addressbook-multiget` | RFC 4791 §7.9, RFC 6352 §8.7 | changed items in batches of 50 at most: a batch answered slowly (20 seconds) or cut makes the next one of that collection half as large, one answered quickly (5 seconds) twice as large again, up to 50 (`dav::pace`) | one GET each (also when a multiget answers nothing) |
| PUT with `If-Match`; a new item with `If-None-Match: *`; 412 | RFC 9110 §13.1 | nobody's change overwritten. On 412 the server's version is kept and yours set aside among the earlier versions, to put back from the window, said. Never an empty `If-Match`, which sabre/dav takes as no condition: an item whose `PUT` was answered without an ETag (a scheduling server changed what it stored) waits for the pull, and a change or deletion made here meanwhile goes after it, over that copy's ETag, when the copy is that write (`ItemState::sent`, a hash without the scheduling parameters); else the usual comparison. A meeting you organize changed so is held to what its guests were told: a force its server sent already goes, and a change its server would not send a guest it tells (or an older version of their times, an Undo while the write was sent) is set aside for the server's copy. The state is saved after each `PUT` or `DELETE` its server takes. A fetch that says no ETag takes the listing's. A `DELETE` refused (412) brings the server's version back, said once | Google takes `If-Match` only: new items go without `If-None-Match` |
| A new item refused because another holds its UID: `no-uid-conflict` (403 or 409, naming that item), Nextcloud's 400, or a 412 | RFC 4791 §5.3.2.1, RFC 6352 §6.3.2.1 | an invitation answered on two devices: the item there (named, else found by a `calendar-query` or `addressbook-query` on the UID) takes the new one's place here, in one file, sent no more. The same answer: nothing said; another answer: the server's kept, and said; a contact or task that differs: yours set aside, as above (`dav::same_uid_there`, `adopt`) | the refusal said, as before |
| An ETag in PUT's answer | RFC 9110 | knowing what the server stored | the item is read back at the pull |
| DELETE with `If-Match` | RFC 9110, RFC 4918 | deletions | — |
| MKCALENDAR with `supported-calendar-component-set` | RFC 4791 §5.3.1 | new task lists and calendars | Google's Calendar API instead (`calendars.insert`, below) |
| Extended MKCOL | RFC 5689 | new address books | not at Google |
| PROPPATCH `displayname` and `calendar-color`; DELETE of an empty collection, or of a whole agenda removed from Your agendas (a dated `.ics` copy kept first) | RFC 4918 §9.2, §9.6 | renaming, recolouring; deleting a list emptied; removing an agenda; a DELETE of a calendar shared with you stops showing it (Nextcloud takes your share away) | Google's Calendar API instead |
| Sharing: DAV header `oc-resource-sharing` or `calendarserver-sharing`; `oc:invite`; POST `oc:share` (`set`, `remove`); `oc-calendar-publishing`, POST `cs:publish-calendar`, `cs:unpublish-calendar`, `cs:publish-url` | Nextcloud's apps/dav and sabre/dav; CalendarServer's caldav-sharing | who sees an agenda, its public link, your availability shared | the line says "This server does not share from Sioul." |
| Your availability on a Nextcloud: PROPPATCH of `schedule-calendar-transp` (RFC 6638 §9.1), `calendar-description` (RFC 4791 §5.2.1), and `calendar-availability` on the scheduling inbox (RFC 7953 §7.2.4, found by `schedule-inbox-URL`, RFC 6638 §2.2); a federated sharee `principal:principals/remote-users/<base64>` (Nextcloud 32 and later) | Nextcloud's apps/dav, sabre/dav | mirrors not counted as your busy time, their day, your working hours told, someone on another Nextcloud | a refusal is tried again a quarter of an hour later, the share waits |
| A named calendar checked by its token alone: REPORT `sync-collection` (RFC 6578) | any CalDAV server that keeps tokens | a phone's background step reading only your availability's calendars | a forgotten token: that calendar synced whole, as at any sync |
| POST to the address book | RFC 5995 | Google's new contacts, when its PUT is refused (403, 405, 409) | — |

**Not used**: `calendar-query` and time ranges to sync (everything is synced, and repeating events are expanded here, `calcard`; a `calendar-query` on a UID only when a new item meets one, above); WebDAV-Push. CalDAV scheduling (RFC 6638) is read, never driven: once a day Sioul asks whether a calendar's server schedules for your addresses (`OPTIONS` for `calendar-auto-schedule`, `calendar-user-address-set`), and each guest of a meeting you organize is told by that server or by your drafts, as their own `SCHEDULE-AGENT` says (below). Free/busy and calendar sharing are the server's own, where it has them (above).

**Sync rounds**: what changed here first, then what changed there; every fifteen minutes and at once after a change in the window; one sync of an account at a time, across processes; a round cut short resumes where it stopped (`dav::tests`).

**A server must keep what it is given.** Sioul writes tasks and cards line by line (`crates/sioul-core/src/lines.rs`) and expects them back as written (`capabilities.rs`: "A CalDAV or CardDAV server keeps everything Sioul writes"; Google is the exception, [google.md](google.md)). A server that validates may refuse what the standard forbids:
- **sabre/dav** (Nextcloud's and Baïkal's server) checks RFC 5545 §3.8.2.3 in a VTODO: `DUE` must have `DTSTART`'s value type and come after it. A task whose start has a time while its date asked is a date, or comes after it, is refused (415). Since 27 October 2026 no writer of Sioul's writes one (`tasks::dates_lines`: a start after its due becomes the due; a day to start beside a time due is kept by Sioul alone, `X-SIOUL-START`), and the rewrite below mends those written before; one written by another program is said plainly when its server refuses it ("its start and its due date are not of one kind…", `dav::refusal`), and the rest of the list syncs on both ways. So a time given to a step is never its `DTSTART`: it is an event, a "time block" in a calendar of the task list's account (« Planned tasks » unless Tasks ⚙ names another), tied to the task both ways (`X-SIOUL-TASK` and an RFC 9253 `LINK`), so that every calendar application shows it ([tasks.md](tasks.md), "Pinned to a time"). `X-SIOUL-AT`, which Sioul wrote for such a time before time blocks (`tasks::AT`), is read for compatibility and never written: one for today or later becomes a block once, and the line goes from the task.
- **iCloud** keeps reminders upgraded since iOS 13 out of CalDAV: its task lists are not reached ([DAVx⁵'s notes on iCloud](https://www.davx5.com/tested-with/icloud)); its calendars and contacts are, with an app-specific password.
- **Google** keeps less than it is given: [google.md](google.md), and below.

**Invitations**, by mail: iMIP (RFC 6047) carrying iTIP (RFC 5546).
- Read in a message: REQUEST, CANCEL, PUBLISH (`agenda::invitation`).
- Answered: a REPLY by mail to the organizer, from the account the invitation came to, with PARTSTAT ACCEPTED, TENTATIVE or DECLINED (`agenda::reply`).
- Kept: the invitation's event, its METHOD taken out (`agenda::stored`), into the first calendar. Your answer is written on your own ATTENDEE line of that copy (`agenda::stored_answered`, `answered_into`), time by time. Whether a server that schedules itself (RFC 6638) also writes to the organizer when this copy arrives: not checked.
- Inviting people, for meetings you organize only, through the organizer's door ([client.md](client.md)): each guest is told by the server or by a METHOD:REQUEST draft you send, never both; never by an agent, the sync or the command line. Tested against stand-ins only.

### Sharing and agendas on their servers
Agendas made, renamed, recoloured, removed and shared from Agenda ⚙ ▸ Your agendas ([client.md](client.md#agendas-on-their-servers)) were tested against stand-ins alone, small fakes that answer as each vendor's code or documentation shows (`calendars::tests`, `dav::tests::names_colours_removals_and_leaving_go_to_the_server`, all on `dav::stand_in`). **Untested against the real servers**:
- **Nextcloud**: the DAV header's words as a real Nextcloud sends them, `oc:invite` as it answers, the POSTs of `oc:share` and `cs:publish-calendar` and its status codes, `cs:publish-url`'s shape, a group's share, a DELETE of a calendar shared with you (read in its code to take the share away), its trash bin keeping a removed calendar, and what a sharee's own app shows of confidential and private events (read in its code, `CalendarObject.php`, `Calendar.php`, `PublicCalendar.php`).
- **Google's Calendar API**: `calendars.insert`'s answer and the CalDAV address of the calendar made (taken to be `…/caldav/v2/<id>/events/`), `calendarList.patch` with `colorRgbFormat`, `calendars.delete`, `calendarList.delete`, `acl` pages, rules and their ids, the public link's shape, and the refusal when the Calendar API is off in the key's project (`accessNotConfigured`, `SERVICE_DISABLED`).
- **Other CalDAV servers** (Radicale, Baïkal, Fastmail, iCloud…): whether their DAV header says sharing (Baïkal runs sabre/dav, whose sharing plugin it may not load), a DELETE of a shared calendar, PROPPATCH of `calendar-color`.
- **Your availability** ([client.md](client.md#sharing-your-availability); research/availability-sharing.md §7), tested against stand-ins alone (`calendars::tests::availability_marks_calendars_and_writes_working_hours_on_a_nextcloud`, `google_s_public_free_busy_goes_on_and_off_and_never_touches_a_public_calendar`, `dav::tests::a_check_of_named_calendars_reads_nothing_while_nothing_changed`). Worth trying on real servers before relying on them:
  - a Nextcloud with two users and a second instance (32 or later): a mirror shared with a user, with a federated `user@instance` (`principal:principals/remote-users/<cloud id in base64>`, read in Nextcloud's code) and by its link; "Find a time" with and without the transparent marks (`schedule-calendar-transp`), set by the owner and by a sharee; the working hours Sioul writes (`calendar-availability` on the inbox, found by `schedule-inbox-URL` or beside the calendars) shown in Nextcloud's Settings ▸ Groupware ▸ Availability and in "Find a time"; Appointments with Sioul's events, which carry no STATUS (nextcloud/calendar issue 8446);
  - Google: the public free/busy iCal address and what it holds; a `freeBusyReader` rule for an address without a Google account; how long a public rule takes to show;
  - how often readers fetch a mirror's link: another Nextcloud's subscription, Google's "From URL", Thunderbird, cal.com's ICS Feed;
  - a phone's night with the calendar check inside its steps (`dumpsys batterystats --charged`), against the night of 10 to 11 October 2026: no more radio wakes, under 5 mAh more;
  - two devices, one offline for a day then opened, while the other keeps a mirror: nothing older written over it, and whether a 412 on its blocks reaches the earlier versions.

## What Sioul writes in tasks, events and cards
Changed line by line: what Sioul does not edit is kept byte for byte (tests: `tasks::a_change_touches_only_its_lines` keeps another application's `X-OTHER-APP` and an alarm; the contacts' tests keep a photo and `X-OTHER-APP`). A form saved unchanged writes nothing.

| `X-SIOUL-LINK;LINKREL=describedby`, `via`, `related` (a relation that is a URI in `X-SIOUL-REL`, quoted); `VALUE=URI` or `UID` | RFC 9253's LINK, the same | tasks, events | notes (`sioul:note/…`), the message (`mid:`, RFC 2392), drafts, events; RFC 9253's `LINK` read too |
| `X-SIOUL-CONCEPT;VALUE=URI` (tag URIs, RFC 4151) | RFC 9253 §7.3's CONCEPT, the same | tasks | the kind; "needs an open office"; other applications' concepts kept, RFC 9253's read too |
| `X-SIOUL-REFID` | RFC 9253's REFID, the same | tasks, events | the project; RFC 9253's read too |
| `X-SIOUL-START` | non-standard property, RFC 5545 §3.8.8.2 | tasks | a task's start, beside `DTSTART` when that is not before `DUE` (a phone's account manager drops it), in its place when the two are of different value types (a server refuses them); read only where `DTSTART` is gone, never after `DUE` |
| `ESTIMATED-DURATION` | draft-ietf-calext-ical-tasks | tasks | how long it takes |
| `CONTACT;ALTREP="sioul:contact/<UID>"` | RFC 5545 §3.8.4.2 | tasks | the people and offices involved |
| `X-SIOUL-BEFORE`, `X-SIOUL-AFTER`, `X-SIOUL-COST`, `X-SIOUL-GAIN` | non-standard properties, RFC 5545 §3.8.8.2 | tasks, events | time kept around it; costs and gain, 0 to 10 |
| `X-SIOUL-FELT-COST`, `X-SIOUL-FELT-GAIN` (`X-SIOUL-ON`), `X-SIOUL-ESTIMATE-FIRST`, `X-SIOUL-ENERGY`, `X-SIOUL-OFFICE-HOURS`, `X-SIOUL-AREA`, `X-SIOUL-BILLABLE` | the same | tasks | how it was; the first estimate; light or heavy; an office's hours; what it is for; billed or not |
| `X-SIOUL-AT` | the same | tasks | a time given for one day, before time blocks: read, never written; one for today or later becomes a block once (above) |
| `X-SIOUL-TASK` | the same | events | the task a time block is for, by its UID (above); on a leg too, the step it is the time of (part 7, once every device keeps such a leg: [tasks.md](tasks.md), "Getting there and coming back") |
| `X-SIOUL-GITHUB`, `X-SIOUL-GITHUB-REASON` | the same | the local GitHub list only | never sent to a server |
| vCard `CATEGORIES` | RFC 6350 §6.7.1, RFC 2426 §3.6.1 | cards | categories, which Nextcloud Contacts shows as groups; several lines read, written back as one where the first was |
| New cards in vCard 3.0 | RFC 2426 | cards | vCard 4.0 (RFC 6350) is read and kept; a 4.0 line merged into a 3.0 card is written as 3.0 |

**Not read**: contact groups kept as cards of their own (`KIND:group` with `MEMBER` in vCard 4.0, Apple's `X-ADDRESSBOOKSERVER-KIND`): they are not categories here, and such a card shows as a contact.

### A phone's ical4j
Murena's account manager on /e/OS (`foundation.e.accountmanager` 4.3.9-22-ose, a DAVx⁵ built on ical4j 3.2.13 and ical4android 1.1.2; checked on 26 October 2026, its code read in the APK) validates every task and event it uploads. In ical4j 3.2.13, RFC 9253's `LINK`, `CONCEPT` and `REFID` give no validation result at all (their `validate()` returns null, fixed only from ical4j 4.1.0), and the validator's `getEntries()` on it throws: the upload of any task holding one crashes ("NullPointerException"), and since it uploads before it downloads, its whole list syncs neither way while one such change waits on the phone. It also turns any `RELATED-TO` other than a parent, a child or a sibling into a parent (dropping `GAP`), drops a `DTSTART` that is not before `DUE`, and writes a `LINKREL` that is a URI back without its quotes (the next reader cuts the line at the URI's colon).

So since 27 October 2026 Sioul writes those under its own names, with the same parameters and values (`lines::OWN_NAMES`, the writers in `tasks`, `links`, `pairs`, `github`, `blocks`): `X-SIOUL-LINK`, `X-SIOUL-CONCEPT;VALUE=URI` (as text, ical4j would send the tag's comma back escaped), `X-SIOUL-REFID`, a relation that is a URI in `X-SIOUL-REL` beside `LINKREL=related`, the waits as `X-SIOUL-RELATED-TO`, and a task's start in `X-SIOUL-START` where the phone would drop it. RFC 5545 §3.8.8.2 tells every client to keep an X- property it does not know, and the phone does, byte for byte. Both forms are read, so that another program's lines and those written before still count. What is given up: an RFC 9253 client no longer sees Sioul's links, kinds, projects and waits for what they are (none in the chain checked here shows them; cfait reads `DEPENDS-ON`: [the guide's Tasks](https://sioul.aurelienpierre.com/guide/tasks.html#waits-in-other-caldav-programs)).

**The rewrite** (`interop::migrate_folder`, `dav::sync_part`): every task and event of a calendar a CalDAV account syncs, once, in the form Sioul writes now (`interop::own_form`, `migrate_text`): only the lines that change, every other byte as it was; its `SEQUENCE` untouched when only Sioul's lines change, moved on when a `DTSTART` had to go (a day to start beside a time due, which Murena refused at every sync, kept as `X-SIOUL-START`); a start after its due made the due; never a meeting with others (`agenda::with_others`), never a calendar you only read, each item through the one door of every writer (`vdir::write_item`). An event in a list that holds tasks only goes to the calendar for new events, its UID and file name kept (`vdir::move_item`; no writer may put one there any more, `agenda::guard`); with none to take it, it stays as it is, and its server's refusal is said. Done after the sync's pull, each unchanged item sent rewritten over its server's copy (`If-Match`; a task changed there meanwhile comes back as its writer wrote it, and is rewritten at the next pull), every item sent here in that form too; kept as done in the calendar's sync state (`State::interop`, format 1) once a whole sync leaves nothing to rewrite, a refusal for good said and left (400, 403, 409, 415, 422: the item as it is, or its place), a passing error tried again at the next sync, the form not said done meanwhile (5xx, 429, 507, a lost connection; `dav::refused_for_good`); said once, calmly, with the count ("12 tasks and events were rewritten in a form your phone’s account manager can send back too; they read the same here."). The same text gives the same lines on every device: two devices doing it at once send the same item, and nothing is set aside (`dav::tests::two_devices_rewriting_at_once_and_a_task_changed_meanwhile`).

**Checked** on 27 October 2026, with stand-ins of a real list's shapes alone (`interop::tests::every_shape_of_the_stand_in_list_is_rewritten_so_the_phone_sends_it`: the `LINK`, `CONCEPT` and `REFID` lines the check of 26 October found, and the four items Murena refused; fiction otherwise), through a replay of the phone's own code on ical4j 3.2.13 (the checker of that check, its round trip of ical4android 1.1.2): before, 55 of the 112 tasks pass and 57 crash, as on a phone with that account manager; rewritten, all 112 pass, uploaded as they are and after a download, a Done ticked on the phone and an upload, twice; Sioul's own lines come back byte for byte, but for a gap of fourteen days, which ical4j writes `P2W` and Sioul reads as its days; Sioul reads every task the phone sends back as it wrote it (their waits, gaps and starts included); the event, as the phone's `Event.write` validates it, crashes before and passes after. Not yet tried on the phone itself. **While a change made on the phone waits there** (a task ticked before the rewrite), the list stays stuck on the phone, the corrected copies unable to come down: unticking the list in the account manager and ticking it again brings them, that change lost: note which task it was, to mark it again.

**Not checked**: Thunderbird, Apple's Calendar and Reminders, Evolution, KOrganizer, GNOME's applications. Any program that rewrites a task from only what it understands would drop Sioul's lines: costs and ratings may then be lost ([capacity.md](capacity.md), "Ratings may not survive other applications").

## Google
Code and details: [google.md](google.md).
- **Signing in**: OAuth 2.0 for native applications (RFC 8252): the system browser, the answer on `http://127.0.0.1:<random port>`, five minutes at most; PKCE with S256 (RFC 7636), `state`, the ID token's address checked against the one typed. Scopes: `openid email`, `…/auth/calendar`, `…/auth/carddav`, `…/auth/tasks`. Sioul's own client is read at build time (`SIOUL_GOOGLE_CLIENT_ID`, `SIOUL_GOOGLE_CLIENT_SECRET`), else the person's own.
- **Calendars**: Google's CalDAV (`https://apidata.googleusercontent.com/caldav/v2/<address>/user`), events only; no MKCALENDAR or PROPPATCH there: calendars are made, renamed, recoloured, deleted, left and shared through the Calendar API v3 (`https://www.googleapis.com/calendar/v3`: `calendars.insert`, `patch`, `delete`, `calendarList.patch`, `delete`, `acl`), which needs the **Google Calendar API** turned on in the key's project; new items without `If-None-Match`, known by their `Location`. Google adds the calendar's default reminders to every event and shifts floating times; both come back as Google keeps them.
- **Contacts**: Google's CardDAV (`https://www.googleapis.com/.well-known/carddav`), written in vCard 3.0 (`contacts::as_vcard3`); a new contact by PUT, else POST (RFC 5995); no new address book.
- **Tasks**: the Google Tasks API v1 (`https://tasks.googleapis.com/tasks/v1`), each list kept here as a folder of VTODO files; `updatedMin` with deleted and hidden tasks; Google keeps a title, notes, done or not, a day, one level of steps; the rest is greyed in the form, kept in the file here, not sent.
- **Gmail and Google Workspace** (Workspace recognised by its MX): IMAP and SMTP with an app password, or XOAUTH2 after signing in with Google with the person's own key. Gmail's scope is restricted, so Sioul's own key cannot ask for it ([google.md](google.md), "Mail"). Tested against stand-ins only.
- **Tested**: the sign-in's pieces (unit tests); Google Tasks against `tools/google-tasks-stand-in.py`; the Calendar API's calendars, colours and ACL against a stand-in in `calendars::tests`. **Not against Google itself**: the token exchange, its CalDAV and CardDAV answers, Google Tasks' own, the Calendar API's own answers.

## Sharing between devices

## OpenPGP
Code: `crates/sioul-core/src/pgp.rs` (Sequoia, pure-Rust cryptography), `crates/sioul-sync/src/keys.rs`; details: [client.md](client.md), "PGP".
- RFC 9580 messages; PGP/MIME (RFC 3156) written and read; inline PGP read. New keys: Curve25519, three years.
- **GnuPG**: its export is imported (`gpg --export-secret-keys --armor`), public keys exported. Sioul keeps its own keys (`~/.local/share/sioul/pgp/`) and never reads or writes GnuPG's keyring or agent. Keys whose secret part lives on a security key (an OpenPGP card) are used by Sioul itself, through PC/SC, not through GnuPG ([client.md](client.md), "Your keys on a security key"); GnuPG and Sioul share the key when `scdaemon.conf` says `pcsc-shared`, and "Let GnuPG release it" frees it otherwise. Tried with a real key, a YubiKey 5, on Linux on 8 October 2026, its renewal through GnuPG included ([client.md](client.md), "Tried with a real key"); not yet on Windows or macOS.
- **Read as GnuPG writes them**: GnuPG 2.4.4 (Ubuntu 24.04's) writes about one key signature in 128 with a number one octet too long (a zero first, counted in its length), which RFC 9580 forbids and Sequoia refuses: that signature was dropped, and the subkey it binds, or the whole key, read as missing. Every certificate from outside (a file, GnuPG's export, a server, a message) is read with its signatures' numbers in their shortest form too (`pgp::minimal_mpis`), a signing subkey's back-signature among them (GnuPG keeps it in the binding's unhashed area; one level only: a signature embedded in an embedded one, which Sequoia refuses, is left as it came, so that a crafted file nesting thousands never takes the reading thread's stack): the same numbers, outside what is signed, each signature still checked; never anything in a signed area, and only ever shorter (a length said too short is left as it came). Each armored block is read on its own, and the certificates read as they came are kept beside those read repaired, merged by fingerprint (`pgp::certificates_of`): the repair only adds. Found by the CI's test of GnuPG's export failing now and then (14 October 2026); 2.4.9 writes them right.
- Others' keys: Autocrypt headers (Level 1) of messages not forged; the Web Key Directory (draft-koch-openpgp-webkey-service, the advanced address then the direct one); keys.openpgp.org (VKS, by e-mail), on request only.
- **Tested** both ways with GnuPG 2.4: Sioul's signed and encrypted message decrypts in GnuPG with a good signature; GnuPG's encrypted, signed and tampered messages read as such in Sioul ([building.md](building.md), "Testing against a local mail server").

- **Mail**: Maildir, a Maildir++ subfolder per folder (notmuch, mutt); on Windows `!` before the flags, as mbsync writes it; `:` and `!` read everywhere.
- **Calendars and contacts**: vdir, one `.ics` or `.vcf` per item, `displayname` and `color` beside (khal, khard, vdirsyncer, pimsync); the sync's state kept apart.
- **Notes, and the records of projects**: Markdown with front matter; settings, time spent, the projects' file and budgets: TOML.
- **Expected**: none of these programs was run on Sioul's folders.
