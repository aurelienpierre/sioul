# Sorting mail by topic: the evidence

**The question** (5 November 2026): how should Sioul tag each message with topics (health, tax, choir, book club, consulting…), learned on the person's own devices, so that mail can be sorted and found by topic, without a chore to start it or keep it right? Where does a topic live (Sioul's own index, IMAP keywords, folders, Gmail labels, JMAP keywords), what does research on filing mail say, how can categories start with the least work, which model fits a laptop and a phone, and how do topics meet projects, areas, persons, money, papers and the agents?

Researched on 5 November 2026 from the repository (read only, version at 6818115) and public sources: RFCs, server and client documentation, papers. Each piece of evidence carries its kind (trial, survey, log study, qualitative, standard, vendor documentation, source code, own inference) and a grade: **strong** when several independent primary sources agree; **moderate** for one solid primary source or consistent secondary reports; **weak** for a single small study, a forum report or an inference, marked as such.

## 0. What Sioul already has, read from the repository
- **Projects take mail by routes** (`docs/notes-folder.md`, "Routes"; `sioul_core::projects`, `porch::Gate`): a route matches on `from_domains`, `from_addresses`, `subject_contains`, `text_contains`, `attachment_contains`; several projects may match (the first is the home, the others "also concerns"); a conversation follows its project through In-Reply-To and References; mail is tied when it arrives (`links.toml`, `mid:` ↔ `sioul:project/`, `how = "project"`), a tie by hand is `how = "link"`; every routing keeps its reason. Routes are rules written by the person: a project is a matter with an end (a tax return, a client's job), not a standing topic.
- **The Porch's lanes** sort by who and how, not by what: right now (codes), a project, from yourself, filed (lists, no-reply), people, screener, less important accounts, the spam filter's catches, set aside (`docs/porch.md`). Mail in no project has no "what".
- **Areas** (work, admin, leisure) are set on sources (an address, a site, a budget, an agenda), not on messages; Mail's area filter shows the addresses whose area is ticked (`docs/areas.md`). An address for "admin + leisure" mixes health, tax, choir and book club.
- **Categories exist on other objects**: tasks and events carry `CATEGORIES` ("you", "proxy", "joy", "someday", and topics: `docs/tasks.md`); contact cards carry vCard `CATEGORIES`, which the sender lists already read (Safe, Neutral… by category: `docs/porch.md`, "Your contacts' categories"); notes are read as a vault, with tags. There is no topic on a message.
- **The spam filter** (`crates/sioul-learn`, `docs/spam-filter.md`, `docs/research/spam-filter.md`): fastText's supervised classifier (the pure-Rust `fasttext` crate 0.8.0, pinned), each message one line of words then header facts as words, 100 dimensions, character n-grams 3–6, 200 000 buckets, minCount 5; Platt calibration; a time-ordered split (oldest 80 % learned, newest 20 % tested); folded into a table of 64-bit word hashes with one score each, plus bucket scores (about a megabyte for 20 000 words), which every device reads, the phone included, and which travels sealed; the language model stays on the computer that made it. Labels: the person's own words in a per-device label log (`state/spam/labels/<device>.jsonl`, sealed, read by every device); the filter's own verdicts count until corrected; weekly self-training on mains power and idle; a new table replaces the old one only when no worse on the newest mail. The crate's `LossName::OneVsAll` exists (checked in its source, `src/args.rs`, `src/fasttext/train.rs`), so the same pipeline can train independent per-label sigmoids.
- **Keywords on the server and here**: the local store is Maildir; only `$Junk` and `$NotJunk` are kept in file names, as Dovecot's keyword letters with a `dovecot-keywords` file (`sioul_core::maildir::KEYWORDS`, `sioul_sync::fetch::maildir_flags`: "other keywords are not"). The filters (Mail ▸ ⚙) can already *add* an IMAP keyword on the server ("which other mail programs show as a tag; never `$Junk`, `$NotJunk` or `$SioulFiltered`": `docs/client.md`, "Filters"), but Sioul does not read keywords back.
- **The mail index** (`sioul_core::mailcache`): one TSV per folder, a cache rebuilt from the messages, never shared; the unified mailbox (`sioul_core::mailbox`) lists each message once across addresses and folders, with chips (All, Unread, Sent, Spam) and the area filter. Gmail's labels arrive as folders; copies of one Message-ID fold into one row.
- **Virtual Secretary**, Sioul's predecessor by the same author, sorted mail into IMAP folders with an RBF SVM over the mean word vector, one label per folder, reporting 87–90 % accuracy on 6 500 French and English messages from one random 5 % hold-out (`docs/virtual-secretary.md`); Sioul maps its folders to projects (`[[virtual_secretary.map]]`, `rules::FolderMapping`). A random hold-out overstates what a time-ordered test would show (section 4).
- **The AI shield** classifies the topic of mail to a shielded public address (work, a question, the press, thanks, a donation, other) with a cloud model, by the person's choice for that address only (`docs/porch.md`). Topics must not depend on it: the brief says local only.
- **Agents**: per-project consent; health is kept from agents whatever the switch (`docs/mcp.md`, "Per-project access").

## 1. Where a topic can live on the server

### 1.1 IMAP keywords (standard)
- **A keyword is a free name the server may refuse.** IMAP has system flags (`\Seen`, `\Answered`, `\Flagged`, `\Deleted`, `\Draft`) and keywords: "A keyword is defined by the server implementation"; "Servers MAY permit the client to define new keywords in the mailbox" (RFC 9051 §2.3.2). A server says it accepts new ones by listing the special flag `\*` in PERMANENTFLAGS at SELECT: "it is possible to create new keywords by attempting to store those keywords in the mailbox"; a keyword outside that list is ignored or kept for the session only (RFC 9051 §7.1). **Standard, strong.**
- **Limits are allowed, per mailbox.** "If the server has a limit on the number of different keywords that can be stored in a mailbox and that limit is reached, the server MUST send a new PERMANENTFLAGS response code without the special flag `\*`"; a STORE past a limit answers `NO [LIMIT]`, the RFC's own example being "At most 32 flags in one mailbox supported" (RFC 9051 §7.1). **Standard, strong.**
- **Names**: a keyword is an IMAP atom, ASCII only, without space, parentheses, braces, `%`, `*`, `"`, `\` or `]` (RFC 9051 §9, `atom-specials`), compared without case (§9, note 1). JMAP states the same set explicitly: 1–255 characters of `%x21–%x7e`, case-insensitive, returned in lowercase (RFC 8621 §4.1.1). So "Book club" or « Santé » cannot be a keyword as written: a topic's keyword must be an ASCII slug, its display name kept elsewhere. **Standard, strong.**
- **A keyword belongs to one copy in one mailbox**: COPY and MOVE say that "the flags and internal date of the message(s) SHOULD be preserved" (RFC 9051 §6.4.7, §6.4.8), a SHOULD, not a MUST. **Standard, strong.**
- **No standard keyword names a topic.** The IANA "IMAP and JMAP Keywords" registry (updated 1 June 2026) holds `$Forwarded`, `$MDNSent`, `$Junk`, `$NotJunk`, `$Phishing`, `$Important` (RFC 8457), and, since RFC 9979 (Jenkins & Eggert, May 2026, Informational), `$muted`, `$followed`, `$notify`, `$memo`, `$hasattachment`, `$canunsubscribe`, `$MailFlagBit0–2` (Apple's seven flag colours) and a few more; nothing for a category or a label with a name and a colour. Each client invents its own (below). **Standard, strong.**
- **Sieve can set keywords at delivery** (`setflag`, `addflag`: RFC 5232, imap4flags), so a server-side rule could tag before any client sees the mail. Only where the person can edit their server's Sieve script. **Standard.**

### 1.2 Servers
- **Dovecot** (the commonest open-source IMAP server, and the server of most shared hosts): in Maildir, keywords live in the file name's flag letters `a..z`, "only 26 keywords are possible to store in the Maildir"; "if more are used, they're still stored in Dovecot's index files"; the letter-to-name map is the folder's `dovecot-keywords` file, which "must not be directly modified" (Dovecot 2.3 documentation, "Maildir Mailbox Format"). Keywords beyond the 26th then live only in the index, which an index rebuild or a migration can lose (own inference). Dovecot's sample configuration caps a new keyword's name at 50 characters (`mail_max_keyword_length = 50`; vendor configuration, **moderate**). **Vendor documentation, strong** for the 26 letters.
- **Cyrus**: a hard limit of 128 user flags per mailbox, names kept in `cyrus.header`, "not recyclable": once 128 names were ever used in a folder, no new one can be made, and a name cannot be removed (info-cyrus list, Bron Gondwana 2012; earlier post quoting the header's 16×8 bytes, 2010). Renaming a topic many times would burn names for good. **Mailing list, moderate**; current versions not checked.
- **Microsoft 365 / Outlook.com IMAP**: no Microsoft document was found on custom keywords; a client's bug report shows a PERMANENTFLAGS without `\*` on what its reporter took for Exchange (KDE bug 408653), and Exchange 2003 refused messages carrying Thunderbird's tags ("APPEND failed: unknown flag", Mozilla bug 382117). Outlook's categories are not stored on IMAP servers: "IMAP accounts do not store category metadata on the server", and the new Outlook dropped local categories for IMAP accounts (Microsoft Q&A, January 2026, a moderator's answer). **Weak**: to test on a real account.
- **Gmail**: labels, not keywords, are its model. "Gmail treats labels as folders for the purposes of IMAP"; `FETCH X-GM-LABELS` and `STORE +X-GM-LABELS` read and write a message's labels; `X-GM-MSGID` names one message across all its folders and `X-GM-THRID` its conversation (Google, "IMAP Extensions", vendor documentation, **strong**). Gmail's IMAP has been seen to list `\*` in PERMANENTFLAGS (a 2014 IETF list post with a session log, **weak**); keywords set there are not shown in Gmail's own interface (inference: Gmail's interface has labels only). Gmail's five tabs (Primary, Social, Promotions, Updates, Forums) are fixed: "You can only choose from the current categories"; a message dragged to another tab "helps Gmail learn your preferences"; a filter by sender sends future mail to a tab (Google, Gmail Help 3094499, **vendor documentation**). The tabs are not offered over IMAP (not in the extensions' documentation; `X-GM-RAW "category:…"` searches them).
- **Fastmail (JMAP)**: in JMAP an email has a set of `mailboxIds` and "the server may allow it to belong to multiple mailboxes simultaneously (often exposed in a user agent as labels rather than folders)" (RFC 8621 §1.3, §4.1.1). In Fastmail's label mode "each label will appear as a folder in any third party IMAP client", a message with several labels being a copy in each such folder, which costs no quota but which "the IMAP client is likely to download … separately"; archiving removes the Inbox label only (Fastmail Help, "Labels & IMAP", **vendor documentation**). IMAP keywords set by a client are kept and searchable but are not shown in Fastmail's web or mobile apps (MailMate list, 2021; Vivaldi forum, **weak**).

### 1.3 Clients: who shows a keyword
- **Thunderbird (desktop)**: tags are IMAP keywords; its five default tags are `$label1`–`$label5` (Important, Work, Personal, To Do, Later); a custom tag's keyword travels, its name and colour are each installation's own; when the server takes no keywords, tags stay in the folder's local `.msf` summary and no other device sees them (Mozilla bug discussions, Axigen community, codamail help; **moderate**). A bug of Thunderbird 153 left tag changes unsent to the server until a fix on the 155 branch (Mozilla bug 2057187, 2026).
- **Thunderbird for Android / K-9 Mail**: no tags. The request to show keywords has been open since 2017 (thunderbird-android issue #2260, closed as a duplicate of the 2015 groundwork PR #558), and Mozilla Connect's "Tags on Thunderbird Android" idea was still unmet in 2026 (**moderate**).
- **Roundcube**: no tags in its core; a third-party plugin (`thunderbird_labels`) colours rows from Thunderbird's keywords, and its own issue tracker says "proper imap label support is broken in roundcube" (**weak**).
- **Apple Mail**: only the flag's colour, as `$MailFlagBit0–2` (RFC 9979 §3); no tags. Since iOS 18.2 it sorts mail into four fixed categories (Primary, Transactions, Updates, Promotions), reported to run on the device, corrected **per sender** ("Categorize Sender", or "Automatically") (Apple's guide, read through secondary reports; **moderate**).
- **Outlook**: categories for Exchange accounts only (above).
- **Gmail's and Fastmail's own apps**: labels shown, keywords not.
- So a keyword written by Sioul would be seen in Thunderbird on a computer, if the server keeps it, and nowhere else the person is likely to look. **Own inference from the above, moderate.**

### 1.4 Subfolders
- **One place per message**: on every IMAP server but Gmail and Fastmail's label mode, a message sits in one folder. A message about the choir's tax receipt is either in "Choir" or in "Tax". Gmail and Fastmail show labels as several folders holding copies, which a plain IMAP client downloads several times (above).
- **Moving hides**: a client that syncs or notifies only the inbox (most phone apps by default; Apple's Mail app "only has my most recent ones" for one diary participant: Cecchinato et al. 2016) never shows what a rule or a classifier moved out. A wrong move is a lost message until someone looks in the right folder; a wrong tag costs nothing while the message stays where it was (own inference).
- **Conversations break**: replies arrive in the inbox and one's own answers go to Sent, so a conversation filed in "Choir" is spread over three folders unless every new message is moved too; IMAP's SEARCH works in one mailbox at a time (RFC 9051 §6.4.4), and Gmail's `X-GM-THRID` is the only server-side conversation id across folders (RFC 8474's `THREADID` where servers offer OBJECTID). Sent mail is never filed by a server rule.
- **Moves change ids**: a move gives the message a new UID in its new folder (RFC 4315; Sioul follows it by COPYUID: `docs/client.md`, "A move keeps the message here").
- **Two sorters fight**: a Sieve rule, Virtual Secretary or another client's filter moving mail while Sioul moves it too. Sioul already refuses to move mail while Virtual Secretary does (`docs/virtual-secretary.md`).
- **What folders do well**: they survive any client and any reinstall, work on every server, and are the person's own visible structure. Existing folders are the best record of what topics a person already keeps (section 3).

### 1.5 What this means for Sioul (own inference from 1.1–1.4)
- **Sioul's own record is the only place that holds several topics per message, in any language, on every server, and on the phone.** Keywords are refused or capped on some servers (Exchange, Cyrus's 128 for good, Dovecot's 26 in Maildir names), are ASCII slugs, and are shown by one desktop client; folders hold one topic and hide what they hold.
- **Sioul's local Maildir cannot carry topics** in its file names either: it keeps two letters today (`$Junk`, `$NotJunk`), and Dovecot's scheme stops at 26 letters per folder. Topics belong in a store of Sioul's own, keyed by the message's address (`mid:`), as the spam filter's label logs are.
- **Writing to the server is optional output**, never the truth: a keyword mirror for Thunderbird users (only where PERMANENTFLAGS has `\*`, a fixed ASCII slug per topic, never renamed on the server), and a Gmail label mirror where the person wants Gmail's own app to show them. Folder moves stay what they are now: the person's filters and Virtual Secretary's.

## 2. What research says about sorting mail

### 2.1 Filing by hand: costly, partial, and abandoned
- **Whittaker & Sidner (1996)**, interviews and mailbox counts with 20 office workers using Lotus Notes (CHI '96, doi:10.1145/238386.238530): three ways of coping, "no filers", "frequent filers" and "spring cleaners"; filing is hard because a message must be classified when it arrives, before its value is known; "failed folders" hold fewer than three messages. Read here through Grevet et al. (2014), who reproduce its numbers: 47 folders on average, 35 % of them failed, the inbox 53 % of the mailbox. **Qualitative with counts, small sample; moderate.**
- **Fisher, Brush, Gleave & Smith (2006)**, 600 Outlook mailboxes in a technology company (CSCW '06, doi:10.1145/1180875.1180922): inboxes about the same size as in 1996, archives ten times larger; 133 folders on average (median 77), 16 % failed (Grevet et al.'s table). **Mailbox census, work mail only; moderate.**
- **Grevet, Choi, Kumar & Gilbert (2014)**, "Overload is overloaded: email in the age of Gmail" (CHI '14, doi:10.1145/2556288.2557013), interviews and self-reported counts from 19 Gmail users, personal and work accounts apart: 22 labels on average in personal accounts (median 11), 27 in work accounts (median 9), **44 % and 50 % of labels "failed"** (fewer than three conversations); the inbox 52 % of the mailbox, 15 030 messages in personal inboxes, 4 846 unread; work mail is overloaded by status (to do, to read), personal mail also "by type" (advertisements, newsletters, notifications); "some users had trouble setting up labels", and the authors suggest clients that propose "a customized label structure such as automatically labeling emails that the user frequently…". **Qualitative, small sample; moderate.**
- **Cecchinato, Sellen, Shokouhi & Smyth (2016)**, "Finding email in a multi-account, multi-device world" (CHI '16, doi:10.1145/2858036.2858473), a diary study of 16 people with logs: work accounts held 32 folders or labels on average (SD 87.5), personal ones 8.8 (SD 10.1); **18 and 4 of them unused for six months**; work mail was found through folders, personal mail "primarily" through search; finding happened on a laptop (54 %) or a desktop (31 %), on the phone 15 % of the time; personal archives are searched for "important details (e.g. booking references) and documents (e.g. passport)". **Qualitative with logs, 16 people; moderate.**
- **Yahoo Mail** (Grbovic, Halawi, Karnin & Maarek 2014, CIKM, doi:10.1145/2661829.2662018, read in full from arXiv:1606.09296): "70 % of users do not create even a single folder" (citing Koren et al. 2011), and "only 10 % of users are 'active classifiers'", moving more than 10 messages into folders in six months; in their dataset, non-spam **machine-generated mail was 90 %** of messages. **Log study, hundreds of millions of accounts; strong** for web mail.
- **Microsoft's web mail** (Narang, Dumais, Craswell, Liebling & Ai 2017, CHIIR, doi:10.1145/3020165.3020175, abstract only): people with larger mailboxes and more folders search more, the mailbox's size more than its folders; people who organise less search more; heavy use of one strategy goes with less use of the others. **Log study; strong for the correlations, abstract read only.**
- **Topics drift**: in the Enron and SRI corpora, "folders are constantly being created and abandoned, becoming more active and less active, and even their major common topics are changing over time"; people "folder some messages by sender, some by event, some by date"; a new folder has a few examples and is mostly missed (Bekkerman, McCallum & Huang 2004, UMass CIIR IR-418, read in full). The failed and unused folders above say the same from the person's side. **Corpus study and censuses; strong.**

### 2.2 Retrieval: folders do not pay back their cost
- **Whittaker, Matthews, Cerruti, Badenes & Tang (2011)**, "Am I wasting my time organizing email? A study of email refinding" (CHI '11, doi:10.1145/1978942.1979457, read in full): a field study of 345 long-term users of a client with folders, tags, search and threads, over 85 000 refinding actions. Opportunistic access (scrolling, sorting, searching) made **87 %** of accesses, scrolling alone 62 %; folder access 12 %, **tag access 1 %**; a folder access took **58.8 s** on average, a search 17.2 s, a sort 14.0 s, a scroll 25.8 s; 88 % of finding sequences succeeded; "high filers" (median split on the share of mail in folders) were no more successful than low filers and took longer; threads helped. "Preparatory behaviors are inefficient and do not improve retrieval success." **Large field log study in one company's client; strong.**
- A keystroke-level model found sorting into folders slower than searching past about 20 folders (Bälter 2000, CHI, doi:10.1145/332040.332413, cited by Grbovic et al. as "with more than 20 folders, folder-based discovery becomes less effective than search"). **A model, not a measurement; weak.**
- Counterpoint: for files on one's own disk, people kept preferring navigation by folders to search even after a better desktop search came (Bergman et al. 2008, ACM TOIS, doi:10.1145/1402256.1402259). That concerns files the person named and placed themselves, not a stream of other people's mail; the mail studies above point the other way. **Log study; moderate, and of limited transfer.**
- So: a topic should be a **way to look** (a view, a filter, a word to search by), not a place a message must be put to be found. Search, threads and recency carry most finding; a topic narrows them. **Own inference, from strong evidence.**

### 2.3 Sorting by machine: few categories, by sender first
- **Per-person foldering is hard to learn.** On seven Enron and seven SRI users, four classifiers (MaxEnt, naive Bayes, SVM, Winnow) reached below 70 % accuracy in nine of fourteen cases under a time-ordered split; random splits overstate it ("65.8 ± 2.3 % accuracy using 4-fold cross validation, while on time-based splits we can only achieve 38.5 ± 2.5 %" for one user); more training mail did not help steadily, since "email is usually related to other recently received email" (Bekkerman et al. 2004). Virtual Secretary's 87–90 % came from one random 5 % hold-out (section 0), the measure this paper warns against. **Corpus study; strong.**
- **Suggesting, not moving**: MailCat (Segal & Kephart 1999, Autonomous Agents, doi:10.1145/301136.301209; and SwiftFile 2000) offered three folder buttons per message rather than filing it, so that a wrong guess cost nothing; Bekkerman et al. note it as the one earlier work evaluated in time order. **Prototype studies; moderate** (not re-read today).
- **A handful of shared categories, learned from everyone's mail, works where per-person folders did not.** Koren, Liberty, Maarek & Sandler (2011, KDD, doi:10.1145/2020408.2020560) mined popular folder names into thousands of tags at 80 % precision and recall for 72 % coverage (as reported by Grbovic et al.); Grbovic et al. (2014) found that **six latent categories** (human; and shopping, financial, travel, career, social for machine mail) cover about 70 % of traffic and of searches, at precision and recall near 90 %. Their cascade classifies **by sender** first: a light rule pass for the biggest senders (32 % of traffic), a table of senders with known categories, and a content classifier only for the **8 % of traffic** from senders unknown or mixed. Their categories were named by people and filled from users' own folder names voting for senders. **Log study and production system; strong** for web mail at scale, which is mostly machine-made.
- **Products did the same**: Gmail's five fixed tabs, corrected by dragging a message and by a filter per sender (Google Help); Outlook's two (Focused, Other); Apple Mail's four on the device since iOS 18.2, corrected per sender. None lets people make their own categories: "You can't create custom categories" (Google). **Vendor documentation.**
- **What none of them does** is what the brief asks: the person's own topics (health, tax, choir, book club, consulting), which mix human and machine mail and change over the years. The nearest evidence is Bekkerman's (hard, drifting) and Grbovic's (sender carries most of it). **Gap in the evidence**: no study was found of a classifier of a person's own few topics, multi-label, corrected without validation, on personal mail.

### 2.4 How many topics
- Personal accounts: a median of 11 labels in Gmail with 44 % failed (Grevet et al. 2014), 8.8 folders with 4 unused for six months (Cecchinato et al. 2016); six latent categories cover most of Yahoo's traffic (Grbovic et al. 2014). So the live topics of a personal mailbox number **about five to twelve**, a few more for someone who also works from it. **Moderate** (small samples, consistent).
- A topic with fewer than three messages is the commonest failure of hand filing (35–50 % of folders and labels); a topic proposed by Sioul should be one that already has mail (section 3). **Own inference.**

### 2.5 What helps retrieval and calm
- **Topics as views and filters, not places**: the evidence on refinding (2.2) and the multi-device study (finding mostly on computers, phones holding only recent mail) favour tags that leave the message where it is, shown as a filter over the one mailbox and as a search condition.
- **Filing is the cost people avoid** (70 % never make a folder, 2.1); a classifier that files for them removes it, as long as being wrong costs nothing (a wrong tag, not a hidden message) and the person never has to check its work (finding 11 of `docs/research.md`: tracking is work too).
- **Few, at the same level**: Grbovic et al.'s requirements: few categories "so as not to overwhelm the user", "easily interpretable and at the same level of abstraction", covering much of the mail. Sioul's areas (work, admin, leisure) already sit above topics; projects sit below them (a project is a matter with an end; a topic is a standing part of life).
- **Calm** (Sioul's findings 2, 5 and 14): no count per topic, no unread number, no new section appearing on the Porch by itself; the topic shown as a quiet word on the row; a filter chip that is off until chosen. **Own inference.**

## 3. Starting without chores

### 3.1 What the evidence says about starting from few labels
- **Rules written once, as noisy labellers, beat hand labelling.** Snorkel (Ratner et al. 2017, PVLDB 11(3), doi:10.14778/3157794.3157797, arXiv:1711.10160) lets people write "labeling functions that express arbitrary heuristics, which can have unknown accuracies and correlations", combines them without ground truth, and trains an ordinary model on the result: in a user study, experts "build models 2.8× faster and increase predictive performance an average 45.5 % versus seven hours of hand labeling"; across six deployments the trained model gained 132 % over the heuristics alone and came "within an average 3.60 %" of large hand-labelled sets. The model generalises beyond its rules because it learns the words that co-occur with them. **Peer-reviewed system with a user study; strong** that weak supervision works; not measured on mail.
- **Folders as votes, at scale.** Grbovic et al. (2014) labelled about 600 folder names by hand and let users' folders vote for each sender's category (a sender needed at least 50 votes from two folders or more), which gave the training set of their sender classifier. A person's own folders can play that part for that person's topics. **Production system; strong** for the method, inference for one person.
- **A label's name alone can start a topic** when a pre-trained language model is at hand: LOTClass reached "around 90 % accuracy on four benchmark datasets" from "at most 3 words (1 in most cases) per class", then self-training (Meng et al. 2020, EMNLP, arXiv:2010.07245). It needs a BERT-sized model: a computer, not a phone. **Benchmarks on news and reviews; moderate**, untested on mail.
- **A few examples per topic suffice for sentence-embedding models**: SetFit fine-tunes a sentence transformer on pairs from a handful of examples, comparable with billion-parameter prompting methods, multilingual by switching the encoder (Tunstall et al. 2022, arXiv:2209.11055); on the Spam-T5 benchmark, TF-IDF with an SVM scored a macro F1 of 0.33 with 32 labels against SetFit's 0.86, and 0.95 against 0.97 with all labels (`docs/research/spam-filter.md`, Q1). Prototypical networks classify by the distance to each class's mean embedding (Snell, Swersky & Zemel 2017, arXiv:1703.05175). **Benchmarks; moderate**: few-shot favours embeddings, many labels favour linear models on words.
- **A new category with few examples is mostly missed** by a word-level classifier (Bekkerman et al. 2004: "Newly created folders adversely affect the classification accuracy"). **Strong.**
- **Self-training drifts toward its own mistakes** ("confirmation bias": a naive pseudo-labeller "overfits to incorrect pseudo-labels"; keeping a minimum of true labels in each batch is one remedy: Arazo et al. 2020, IJCNN, arXiv:1908.02983). The spam filter's research found the same for spam (poisoning through its own verdicts: Nelson et al. 2008), and Sioul accepted it with guards (`docs/research/spam-filter.md`, section 3). **Strong.**
- **Noisy labels are the normal case**: benchmark test sets hold at least 3.3 % label errors on average, and "lower capacity models may be practically more useful" when labels are noisy (Northcutt, Athalye & Mueller 2021, NeurIPS Datasets, arXiv:2103.14749); human labels in mail err 3–7 % (Cormack & Kołcz 2009, in the spam note). Linear models with regularisation tolerate moderate noise (Frénay & Verleysen 2014, IEEE TNNLS, doi:10.1109/TNNLS.2013.2292894, a survey; not re-read today). **Strong.**
- **Machine clusters are not always meaningful to people**: topic models with better held-out likelihood can infer topics people find less coherent (Chang, Boyd-Graber, Gerrish, Wang & Blei 2009, "Reading tea leaves", NeurIPS; known work, not re-read today). A cluster Sioul proposes should be shown by what people recognise (its senders and a few subjects), never by its top words. **Moderate.**
- **Active learning** (asking for labels where the model doubts) gave the largest gains for spam (TREC 2007; `docs/research/spam-filter.md`, Q3), but Sioul refused it as a chore: "nothing asks for a label". The same refusal applies here. **Strong evidence, refused by rule.**

### 3.2 Seeds Sioul already holds (from the repository; inference for their quality)
Each seed below is a labelling rule in Snorkel's sense: it labels many past messages at once, is right most of the time, and is overruled by the person's own word.
1. **The person's folders**: each folder of the corpus (`corpus::Record.folder`) is a candidate topic, its mail the examples; Virtual Secretary's folders are already mapped to projects (`[[virtual_secretary.map]]`). Folders with fewer than about 20 messages, system folders (`folders::Role`), and folders unused for a year are left out (the "failed folders" of 2.1). The best seed: it is the person's own sorting, done before.
2. **Projects and their routes**: each project's mail (routes, ties, conversations: `projectview::mail_of`) labels that project's topic; a project names its topic once (`taxes-2025` → Tax), and projects of the same kind share it (`taxes-2024`, `taxes-2025`). Mail a route takes is checked by `porch::Gate` already, so forged mail seeds nothing.
3. **Contacts' categories** (vCard `CATEGORIES`, Nextcloud's groups): a category "Chorale" on twelve cards makes their mail a seed for Choir. Already read by the sender lists (`contacts::category_key`).
4. **Senders known by kind elsewhere in Sioul**: a site's type and category (`docs/sites.md`), a contract's counterparty and kind (insurance, energy, a lease: `sioul-contracts.toml`), a budget's payees (`sioul-budgets.toml` lines with their `links` to mail), papers kept from a mail with their kind (a tax notice: `papers.md`), a letter's sender and kind. These name machine senders (offices, banks, insurers), the 90 % of mail that Grbovic et al. found machine-made.
5. **Task and event categories**: a task made from a message (`X-SIOUL-LINK;LINKREL=via`) with a category that is a topic labels that message.
6. **The person's own words**, given once, as they come: "+ Topic" on a message, and "Always for this sender" (Apple Mail's "Categorize Sender", Gmail's filter by sender).

### 3.3 Recommended start (own inference from 3.1–3.2)
- **Day one, nothing to do**: Sioul reads the seeds above, groups them into at most twelve proposed topics (a folder, a project kind and a contact category that share senders become one topic, named after the folder or the category as the person wrote it), and tags past and new mail from the seeds alone. One card, once, in an admin window: "Sioul sorted your mail into 7 topics from your folders, projects and contacts: Tax, Health, Choir… You can rename, join or remove them in Mail ▸ ⚙ ▸ Topics." No button needs pressing.
- **A topic needs mail to exist**: proposed only with at least 20 messages from at least 3 senders, or 50 from one (a single office). Below that it waits, listed under "Too few messages yet" in the settings.
- **The person's own topic** starts from a name and one message ("+ Topic" ▸ "Book club"): its seeds are then the message's sender, its conversation, and, at the next training, the mail that resembles it; until the model has 20 examples it tags by sender and conversation only, and says so in the settings ("Sorted by its senders until it has more mail").
- **Groups Sioul noticed** (clusters of senders whose mail goes together and that no topic covers) are listed in the topics' settings by their senders and two subjects, with "Name it"; never on the Porch, never asked.

## 4. The model

### 4.1 What fits, and why (evidence and inference)
- **Sioul's choice** ([topics.md](../topics.md)): one topic per message at most, so one model, fastText's softmax over every topic, trained once. What else a message relates to is kept apart from topics: the person it concerns, the area, the project, the money it moves. The one-vs-all route below, which several topics per message would need, was the first recommendation.
- **fastText's classifier, one-vs-all, on the spam filter's pipeline.** fastText's tutorial: "A convenient way to handle multiple labels is to use independent binary classifiers for each label. This can be done with `-loss one-vs-all` or `-loss ova`", with predictions kept above a probability (0.5 in its example), since softmax's probabilities "must sum to 1" and make multi-label thresholds "tricky and unintuitive" (fastText documentation, "Text classification" tutorial; Joulin et al. 2017, EACL, arXiv:1607.01759, for the model). The pinned Rust crate implements it (`fasttext` 0.8.0: `LossName::OneVsAll`, "OVA ignores target_index; all labels in `labels` are positives", `src/fasttext/train.rs`; checked in its source today). **Vendor documentation and source code; strong.**
- **It folds the same way** (own derivation from `docs/spam-filter.md`, "The fold, the classifier's"): with one-vs-all, topic k's probability is the sigmoid of `f_k = w_k · h`, with `h` the mean of the input rows the line reads; so each row folds into K scalars `w_k · row`, and the table keeps K numbers per known word and per bucket instead of one. With K = 12 topics, 20 000 words and 200 000 buckets as the spam table has them, that is about 10 MB in f32; with 50 000 buckets and scores in f16, about 2 MB (word hashes included). **Own inference**; the bucket count and precision must be measured against fastText's own predictions within the spam table's 1e-4 tolerance (looser in f16: to set in phase 0).
- **The sender carries most of a topic**: Grbovic et al. (2014) classified 92 % of traffic by sender alone and sent only the rest to content. So each line carries, beside the words, the **authenticated** sender as tokens (`from:<address hash>`, `from-dom:<aligned DKIM or SPF domain>`, `list:<List-Id>`), only when Sioul's own checks pass (`corpus::Checked`), so that forged mail cannot borrow a sender's topic; and a rule layer above the model applies the person's per-sender choices. **Strong for the principle, inference for the tokens.**
- **Rules plus a model, in this order** (as Sioul's spam filter orders its words, `docs/porch.md`, "The order of words"): the person's word on the message > the person's word on the sender ("Always" / "Never" for a topic) > a project's route or tie, and the conversation of a message already tagged > the other seeds > the model. Each tag keeps its reason ("Choir · from your contacts' category Chorale", "Tax · in the project Income tax 2025", "Health · Sioul's guess"), as routes keep theirs.
- **Local embeddings, measured, not adopted first.** A sentence encoder is the better few-shot learner (3.1), but: the spam filter's research found a frozen centroid weaker than fastText's supervised classifier once labels were many, on one real mailbox; a transformer needs an inference runtime and a model of a hundred megabytes or more on the phone, on older phones too (the build is measured on a GS6: `docs/android.md`), for every message of the background step (inference). A static distilled model (Model2Vec's potion-multilingual-128M: 101 languages, 256 dimensions, means of token embeddings, a classification score of 52.4 on MTEB against LaBSE's 90.9 % overall; Minish Lab model card, **vendor documentation**) keeps the fold: a linear head over a mean of token embeddings folds into one score per token, like fastText's. Recommended as the one alternative to measure in phase 0, for topics with fewer than 50 examples. **Own inference.**
- **What runs where**: training on a computer on mains power and idle, weekly with the spam filter's run (`sioul_learn::auto`), on the same corpus (its ham only, every folder but Trash, Drafts and Sent); the phone never trains, reads the folded table, and judges new mail in its background step, as for spam (`docs/spam-filter.md`, "The phone"). Nothing leaves the person's devices; the language model stays on the computer that trained it; the table travels sealed (word hashes and numbers, no word). **Built pattern; strong.**

### 4.2 Several topics, and doubt (the first recommendation; Sioul keeps one topic per message)
- **Multi-label**: each topic its own sigmoid, calibrated by Platt on mail the model did not learn from (the spam filter's per-group newest fifth), so that 0.8 means about 0.8 for every topic. **Built pattern.**
- **Three outcomes per topic, as for spam**: *sure* from a high threshold (recommended start: the lowest score whose precision against the seeds on the newest fifth is at least 0.9, never below 0.7); *maybe* from 0.5 to it; *no* below. Sure tags show on the row and in the topic's filter; maybe tags show only at the end of a topic's filter, folded, under "Perhaps", and nowhere else; at most three topics shown on a row, the surest first. **Own inference** from the spam filter's bands and SpamBayes' "unsure" (spam note, Q4).
- **No topic is a valid answer**: mail from shops, newsletters and notifications often fits none of the person's topics. Grbovic et al.'s categories covered 70 % of traffic, not all. A message with no sure topic shows nothing. **Strong.**

### 4.3 Learning from corrections, measuring without validation
- **Labels, best first** (the spam filter's order, `docs/spam-filter.md`, "The labels"): the person's acts on a message (add, remove), newest winning, logged per device in a topic label log that travels sealed; the person's sender rules; seeds; then sure tags of the previous table, which count until corrected (the spam filter's choice for its own verdicts); maybe tags never count. A removed tag is a negative for that topic only.
- **Guards against drift into its own mistakes** (3.1, Arazo et al.; Nelson et al. for spam): every training keeps all seeds and the person's words at full weight; the model's own sure tags weigh less than a seed (recommended 0.5) and never more than half of a topic's examples; a sender's or a conversation's weight in one topic is capped (recommended 20 % of its examples), so that one newsletter cannot become "Book club". **Own inference.**
- **A new table replaces the old only when no worse**, on the newest mail neither learned from: its agreement with the seeds and with the person's corrections, per topic, at least the old table's; and its **churn** (the share of already shown tags it would change) under 2 %, since the layout must not move under the person's eyes (finding 2). Changed tags on old mail appear at the next opening, never while a list shows. **Own inference.**
- **Measured without asking anyone**, numbers printed by `sioul topics eval` and kept in the table's metadata, never shown as a score in the window:
  - per topic, on a time-ordered split (oldest 80 % learned, newest 20 % tested: Bekkerman et al.'s lesson: a random split gave one user 65.8 % where the time-ordered one gave 38.5 %), precision and recall against seeds and corrections, with the warning that seeds are noisy (3–7 % as human labels are);
  - the **correction rate**: corrections per hundred sure tags shown, per topic and month, from the label logs (shown tags are logged by count only);
  - churn between tables; coverage (the share of mail with a sure topic).
  The correction rate is biased toward what the person looks at; it is a measure of the annoyance, which is what matters here. **Own inference.**

## 5. How topics meet the rest of Sioul (own inference, from the repository)
- **Three questions, three dimensions**: an *area* says when a thing may come (work, admin, leisure: set on sources); a *topic* says what a message is about (a standing part of life: health, tax, choir); a *project* is a matter with an end (Income tax 2025), and a *person* is whom it concerns (a child). Topics sit between areas and projects and must not replace either.
- **Projects**: a project names a topic (`topic = "tax"` in `sioul-projects.toml`); its mail is a seed for it; a new project of a known topic is offered that topic's senders as routes ("Mail from impots.gouv.fr comes to Tax: take it here too?", in the project's form, once). A project's lane on the Porch is unchanged: topics add no lane.
- **Areas**: a topic has an area (Health → admin, Choir → leisure, Consulting → work), proposed from where its mail arrives and the seeds' areas (a project for a client is work). Mail's area filter could then show a consulting message that came to a personal address in work time. That changes the one matrix of what reaches the person (`docs/attention.md`), so the first phases use the topic's area in Mail's filter only, never for notifications; the matrix's use of it is a later decision.
- **Persons**: a child's school mail is a topic (School) for a person (the child); persons stay their own tie (`links.toml`, `sioul:person/…`, by the sender's address on the person's cards). A topic may name a person (`person = "<id>"`: "School · Léa"), so that the topic's mail shows on the person's page. A person closed to agents keeps their topic's mail from agents too.
- **Money**: the ledger's mail history (`payments.rs`, movements' mail sources) is a seed: mail joined to movements of a budget that names a topic (`[[budget]] topic`) labels that topic, and a topic's filter on Mail shows the money mail of its budget. Money is read as now; topics change nothing in Budgets.
- **Papers, contracts, letters, sites**: "Keep in papers" from a mail gives the paper's kind; a kind maps to a topic (tax notice → Tax; health card, prescription → Health), seeding the message and its sender. A contract's counterparty (insurance, energy, lease) and a site's category do the same. Letters (paper) can carry the topic of their sender, so that one topic's filter on the Letters page and in Mail tells the whole story; later phase.
- **Tasks and events**: `CATEGORIES` already holds topics; a task made from a tagged message takes its topics as categories (one line, each name once), and a task's category that is a topic tags the message it was made from. One vocabulary across mail, tasks and events; contacts' categories stay the sender lists' own, read as seeds only.
- **The agents' tools**: `mailbox`, `search_mail` and `find` take `topic` and give each message's sure topics; a topic has "Open to AI agents" as a project has (`ai = true`). A topic whose name or seeds say health (health, santé, médical, a health paper's kind) starts closed, and its *maybe* tags count for keeping mail out, so that doubt keeps mail from agents rather than lets it through; health stays kept by the rules of `docs/mcp.md` whatever the topic says.
- **The AI shield's topics** (work, a question, the press…) stay the shield's own, for a public address only.

## 6. What the evidence does not settle
- No study was found of a classifier of a person's own handful of topics on personal mail, multi-label, corrected only by the person's spontaneous acts. Everything about accuracy here is inferred from foldering on work corpora (Bekkerman et al.), from web-scale fixed categories (Grbovic et al.) and from Sioul's spam filter on one mailbox.
- How many corrections people make without being asked, and whether a wrong tag annoys more than no tag, is unmeasured; the correction rate (4.3) is the proposed measure.
- How servers treat a keyword written on a Gmail message that has several labels (one copy or all), whether Microsoft 365 accepts any keyword, and whether Thunderbird shows a keyword it has no tag for: to test on real accounts.
- French mail: no topic-classification evaluation on French personal mail was found; character n-grams and Sioul's tokenizer serve both languages for spam, untested for topics.
- Whether sender tokens make the model learn senders only (as `Sender:` became SpamBayes' strongest token: spam note, Q3), so that a known topic's new sender is missed: measured in phase 0 by a slice of new senders.
